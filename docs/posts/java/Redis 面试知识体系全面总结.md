# Redis 面试知识体系全面总结

> 本文整理自 5 篇 Redis 面试高频文章，覆盖核心数据结构、持久化、高可用架构、缓存设计、分布式锁、过期与淘汰策略、事务/Lua/Pipeline、应用场景及性能原理等关键考点。

---

## 一、核心数据结构及底层编码

### 1.1 五大基础类型

| 类型 | 底层编码 | 典型场景 |
|------|---------|---------|
| **String** | SDS（简单动态字符串） | 验证码、Token、计数器、对象序列化存储 |
| **List** | quicklist（ziplist + 链表） | 消息队列、任务列表、文章列表 |
| **Hash** | ziplist（小数据量）/ dict（大数据量） | 对象存储（用户信息）、购物车 |
| **Set** | intset（全整数）/ dict | 去重、共同好友、抽奖（SPOP/SRANDMEMBER） |
| **ZSet** | ziplist（小数据量）/ skiplist + dict | 排行榜、延迟队列 |

### 1.2 三种扩展类型

- **Bitmap**: 紧凑的二进制位存储，适合签到统计、在线用户标记。1亿用户签到仅需约12MB。
- **HyperLogLog**: 基数统计，误差率0.81%，仅需12KB即可统计海量UV。
- **GEO**: 经纬度存储与距离计算，适用于"附近的人/商家"功能。

### 1.3 底层关键结构详解

#### SDS（简单动态字符串）

- 预分配空间，避免缓冲区溢出。
- O(1) 获取字符串长度（传统 C 字符串需 O(n) 遍历）。
- 二进制安全：可存储任意二进制数据，不以 `\0` 作为结束标志。
- 惰性空间释放：缩短字符串时不立即回收内存，减少重分配次数。

#### 跳表（skiplist）

- 多层索引链表结构，平均查找复杂度 O(logN)。
- 替代平衡树实现有序集合（ZSet），实现更简单，范围查找更高效。
- 层数随机生成，最高层为索引层，最底层包含所有元素。

#### 压缩列表（ziplist）

- 连续内存存储，无指针开销，内存利用率高。
- 适合小数据量场景（元素少且值短）。
- 大数据量时会升级为 dict（哈希表），存在级联更新（连锁更新）风险。

#### 字典（dict）

- 哈希表实现，支持渐进式 rehash，避免一次性迁移大量数据导致阻塞。
- 负载因子超过阈值时自动触发扩容或缩容。

#### quicklist

- 双向链表 + ziplist 的混合结构。
- 每个节点是一个 ziplist，兼顾内存效率和遍历性能。
- Redis 3.2+ 的 List 底层默认实现。

### 1.4 对象存储选型建议

| 维度 | String + JSON | Hash |
|------|--------------|------|
| 读写方式 | 整体读写 | 可单独读写某字段 |
| 序列化开销 | 每次需整体反序列化 | 仅操作目标字段 |
| 内存占用 | 略小 | 略大（额外指针开销） |
| 适用场景 | 字段不频繁修改、数据量小 | 字段频繁修改、需部分读写 |

**建议**: 大部分场景使用 String + JSON 序列化即可，简单通用。

## 二、持久化机制（RDB / AOF / 混合持久化）

### 2.1 RDB（快照）

#### 工作原理

在某一时间点生成内存数据的全量二进制副本（dump.rdb 文件）。

#### 触发方式

| 方式 | 命令 | 特点 |
|------|------|------|
| 同步 | `save` | 阻塞主进程，生产环境禁用 |
| 异步 | `bgsave` | fork 子进程执行，不阻塞主进程 |
| 自动触发 | 配置 `save 3600 1 300 100 60 10000` | 在时间窗口内 key 变化达到阈值时触发 |

#### Fork 与 COW（写时复制）机制

- `bgsave` 通过 `fork()` 创建子进程，fork 操作本身是阻塞的，耗时随数据量增大。
- 子进程与父进程共享内存页，父进程写数据时才会复制对应内存页（COW）。
- 高并发写入会导致大量内存页被复制，内存使用量可能翻倍。
- **必须禁用 Linux 透明大页（THP）**：THP 以 2MB 为单位复制，会极大增加 COW 内存开销，甚至导致 OOM。

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 文件体积小，适合灾备和传输 | 可能丢失两次快照间的数据变更 |
| 恢复速度极快（直接加载二进制） | fork 大内存时可能短暂阻塞 |
| 父进程无磁盘 I/O 负担 | 旧版 RDB 格式兼容性差 |

### 2.2 AOF（追加日志）

#### 工作原理

以文本协议格式记录每条写命令，追加到 AOF 文件末尾。流程包含：追加 -> 写入内核缓冲区 -> 刷盘 -> 重写 -> 加载。

#### 刷盘策略（fsync）

| 策略 | 原理 | 数据安全 | 性能 | 数据丢失风险 |
|------|------|---------|------|-------------|
| `always` | 每次写后立即刷盘 | 最高 | 极差 | 无 |
| `everysec` | 后台线程每秒刷盘 | 较高（推荐） | 较好 | 最多1秒；磁盘I/O繁忙时最多2秒 |
| `no` | 交由操作系统控制（约30秒） | 较低 | 最佳 | 可能丢失30秒数据 |

#### 记录时机

- 在命令执行后记录 AOF 日志，省去语法检查且不阻塞当前指令执行。
- 但刚执行完若宕机会丢失该操作。

#### 重写机制

- **目的**: 压缩文件体积，去除冗余命令（如多次修改同一 key，只保留最终值）。
- **自动触发条件**: `auto-aof-rewrite-min-size`（最小体积）和 `auto-aof-rewrite-percentage`（增长百分比）。
- **重写过程**:
  1. fork 子进程根据当前内存状态生成最小命令集的新文件。
  2. 重写期间的增量命令暂存于重写缓冲区。
  3. 子进程完成后，将缓冲区内容追加到新文件末尾。
  4. 原子替换旧文件。

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 数据安全性高（最多丢1秒） | 文件体积大 |
| 文件可读，可手动修复误操作 | 恢复需逐条执行命令，速度慢 |
| 无断电损坏风险 | 无校验和，依赖逐条语法解析 |

### 2.3 混合持久化（Redis 4.0+ 引入）

#### 原理

AOF 重写时，子进程将当前内存快照以 **RDB 格式**写入文件头部，重写期间的增量命令以 **AOF 文本格式**追加到文件尾部。结合了 RDB 加载快和 AOF 数据安全的优势。

#### 配置

```conf
aof-use-rdb-preamble yes    # 开启混合持久化（7.0+ 默认开启）
```

#### 校验机制

- RDB 部分：包含 CRC64 校验和。
- AOF 部分：仅做语法解析。

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 加载速度比纯 AOF 快数倍 | 文件头部为二进制不可读 |
| 数据丢失窗口极小 | 压缩解压需额外 CPU |

### 2.4 Redis 7.0 Multi-Part AOF 架构

#### 架构设计

将单一 AOF 文件拆分为多个文件：

| 文件类型 | 说明 |
|---------|------|
| BASE | 基础文件（RDB 或 AOF 格式的全量数据） |
| INCR | 增量文件（记录重写期间的增量命令） |
| HISTORY | 历史文件（归档旧文件） |
| manifest | 清单文件（统一调度所有文件） |

#### 优势

- 彻底消除重写期间的内存缓冲开销与双重 I/O 写入问题。
- 重写过程更轻量，不需要 fork 子进程合并缓冲区。

#### 风险

- 清单文件是核心元数据，一旦损坏或丢失数据库将无法恢复，必须纳入常规备份策略。

### 2.5 生产环境选型指南

| 场景 | 建议方案 |
|------|---------|
| 纯缓存 | 关闭或低频快照即可，数据可从 DB 重建 |
| 核心业务 | 启用 7.0 多文件架构，不应将 Redis 作为唯一数据源 |
| 主从集群 | 主节点关闭落盘，由从节点承担 AOF 持久化 |

**关键监控指标**:

- 快照耗时及 COW 内存占比
- 内存碎片率（RSS/USED 应 < 2）
- AOF 刷盘延迟阻塞次数
- 磁盘空间使用率

## 三、主从复制、哨兵、集群

### 3.1 主从复制

#### 核心作用

- 读写分离，提升读性能。
- 数据备份，为高可用提供基础。

#### 同步机制

**全量同步（首次连接）**:

1. 从节点发送 `PSYNC ? -1` 请求全量同步。
2. 主节点执行 `bgsave` 生成 RDB 文件，期间增量命令写入复制积压缓冲区（repl_backlog，默认1MB环形缓冲区）。
3. RDB 传输给从节点，从节点加载。
4. 将缓冲区中的增量命令发送给从节点执行。

**增量同步（断线重连）**:

1. 从节点携带自身复制偏移量（offset）发送 `PSYNC offset runid`。
2. 主节点判断 offset 是否在 repl_backlog 范围内。
3. 若在范围内，返回 `+CONTINUE`，从 offset 位置开始发送增量数据。
4. 若不在范围内（断线太久），返回 `+FULLRESYNC`，重新全量同步。

#### 异步复制与脑裂问题

- **异步复制**: 主节点不等待从节点确认，写完即返回。性能高但极端情况可能丢数据。
- **脑裂**: 网络分区导致原主节点继续接收写请求，恢复后降级为从节点会丢失数据。
- **预防措施**:

```conf
min-slaves-to-write 1          # 至少1个从节点在线才允许写入
min-slaves-max-lag 10          # 从节点延迟不超过10秒
```

### 3.2 哨兵（Sentinel）

#### 核心功能

1. **监控**: 定期检测主从节点是否正常运行。
2. **自动故障转移**: 主节点故障时自动选举从节点提升为新主。
3. **配置中心**: 客户端通过 Sentinel 发现当前主节点地址。
4. **通知**: 故障转移后通知客户端和从节点更新配置。

#### 下线判定

| 状态 | 说明 |
|------|------|
| 主观下线（SDOWN） | 单个 Sentinel 在超时时间内未收到节点有效回复 |
| 客观下线（ODOWN） | 法定人数（quorum）的 Sentinel 均认为该节点主观下线 |

#### 故障转移流程

1. **选举 Leader Sentinel**: Sentinel 之间基于 Raft 算法投票选出 Leader。
2. **选择最优从节点**: Leader 根据以下优先级挑选：
   - 从节点优先级（priority）
   - 复制偏移量（数据最新程度）
   - RunID 字典序（兜底排序）
3. **提升为主节点**: 向选中的从节点发送 `SLAVEOF no one`，其他从节点切换复制目标。
4. **旧主恢复后**: 自动降级为从节点，从新主同步数据。

#### 部署建议

- 至少 3 个 Sentinel 节点（奇数，避免脑裂）。
- quorum 设置为 Sentinel 节点数的一半加一。
- 典型架构：一主两从 + 三个 Sentinel。

### 3.3 Cluster 集群

#### 核心设计

解决单机容量和性能瓶颈，将数据分散到多个主节点，实现数据分片和高可用。

#### 哈希槽机制

- 总共 **16384** 个哈希槽（hash slot）。
- Key 通过 `CRC16(key) % 16384` 映射到对应槽。
- 每个主节点负责一部分槽，所有槽必须被覆盖集群才可用。

#### 节点通信

- 采用 **Gossip 协议**，节点间定期交换状态信息。
- 消息类型：PING、PONG、MEET、FAIL。
- 通过消息传播实现集群状态的一致性。

#### 扩缩容

- **扩容**: 将部分槽及其数据从现有主节点迁移到新主节点。
- **缩容**: 将要下线节点的槽迁移到其他节点。
- 扩缩容期间服务可用，客户端通过 `MOVED` 或 `ASK` 重定向到正确节点。

#### 高可用

- 每个主节点配备至少一个从节点。
- 主节点故障时，从节点自动接管其槽。
- 若某槽的主从节点均故障，该槽不可用。

## 四、缓存穿透 / 击穿 / 雪崩

### 4.1 缓存穿透

#### 定义

请求的数据在缓存和数据库中均不存在，每次请求都穿透缓存直接打到数据库。

#### 常见场景

- 恶意攻击：构造大量不存在的 key。
- 业务异常：查询条件错误导致永远查不到数据。

#### 解决方案

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| 参数校验 | 先过滤非法请求（如负数ID、超长字符串） | 最简单，但无法应对合法格式的恶意请求 |
| 缓存空值 | 将不存在的 key 缓存为空值，设置短过期（2~5分钟） | 简单有效，但大量空值会占用内存 |
| 布隆过滤器 | 在缓存前置一层，拦截不存在的 key | 内存效率高，但存在误判率（将存在判断为不存在），且不支持删除 |

#### 布隆过滤器要点

- 由多个哈希函数和位数组组成。
- **可能误判元素存在，但绝不会误判元素不存在**。
- 误判率可通过调整位数组大小和哈希函数个数来控制。
- 标准布隆过滤器不支持删除（可用 Counting Bloom Filter 替代）。

### 4.2 缓存击穿

#### 定义

某个被大量请求访问的**热点 key** 突然过期，大量并发请求同时打到数据库。

#### 与穿透的区别

穿透是查不存在的数据；击穿是热点数据过期瞬间的并发压力。

#### 解决方案

| 方案 | 原理 | 适用场景 |
|------|------|---------|
| 永不过期 / 长过期时间 | 热点数据不设置过期或设置超长过期 | 访问频率极高的核心热点数据 |
| 提前预热 | 在过期前主动刷新缓存 | 可预知过期时间的数据 |
| 互斥锁（setnx） | 重建缓存时仅允许一个线程操作，其他线程等待或返回默认值 | 通用场景，需注意死锁 |
| 逻辑过期 | 数据中记录逻辑过期时间，过期后由后台线程异步更新 | 对实时性要求不高的场景 |

### 4.3 缓存雪崩

#### 定义

大量缓存 key **同时过期**或 Redis 宕机，所有请求同时打到数据库，导致数据库压力骤增。

#### 与击穿的区别

击穿是单个热点 key；雪崩是大量 key 同时失效。

#### 解决方案

| 方案 | 原理 |
|------|------|
| 随机过期时间 | 在基础过期时间上加随机值，避免集中过期 |
| 多级缓存 | 本地缓存（Caffeine/Guava）+ Redis，降低对单一缓存的依赖 |
| Redis 高可用 | 主从 + 哨兵或 Cluster 集群，避免单点故障 |
| 限流降级 | 兜底方案，保护数据库不被压垮 |
| 缓存预热 | 系统启动前预先加载热点数据到缓存 |

### 4.4 缓存与数据库一致性

#### 旁路缓存模式（Cache Aside Pattern）

**读流程**: 先读缓存 -> 缓存未命中则读 DB -> 写入缓存。

**写流程（推荐）**: 先更新数据库 -> 再删除缓存。

#### 为什么是删除缓存而非更新缓存

- 更新缓存在并发写场景下可能出现旧值覆盖新值。
- 删除缓存在下次读时自然会加载最新值。

#### 删除缓存失败的处理

| 方案 | 原理 |
|------|------|
| 重试机制 | 删除失败后多次重试，直到成功 |
| 消息队列 | 将失败的 key 存入消息队列，异步重试删除 |
| 设置较短过期时间 | 兜底方案，即使删除失败也会在过期后自动更新 |

#### 延迟双删（不推荐）

更新前先删缓存 -> 更新 DB -> 延迟一段时间再删缓存。复杂且不可靠，延迟时间难以确定。

## 五、分布式锁

### 5.1 Redis 基础分布式锁

#### 加锁

```bash
SET key unique_value NX EX seconds
```

- `NX`: 仅当 key 不存在时设置（保证互斥）。
- `EX seconds`: 设置过期时间（防止死锁）。
- `unique_value`: 唯一标识（如 UUID），防止误删他人的锁。
- **必须是原子操作**：SET NX EX 是 Redis 的单条原子命令。

#### 解锁（Lua 脚本保证原子性）

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

- 先比较值再删除，必须在同一个 Lua 脚本中执行，保证原子性。
- 若用 GET + DEL 两步操作，可能在 GET 和 DEL 之间锁已过期并被其他客户端获取。

#### 固有缺陷

若业务执行时间超过 TTL，锁提前失效，可能引发并发冲突。无法自适应业务执行时间。

### 5.2 Redisson + 看门狗（Watch Dog）

#### 自动续期机制

- 未手动指定超时时，默认锁有效期 30 秒（`lockWatchdogTimeout`）。
- 后台线程（看门狗）每 **10 秒**（默认值，为有效期的 1/3）执行 Lua 脚本将 TTL 重置为 30 秒。
- 直到业务主动调用 `unlock()` 释放锁，看门狗才停止续期。

#### 可重入设计

- 底层利用 Hash 结构记录：
  - field: 线程标识（UUID + threadId）
  - value: 重入次数
- 同一线程多次获取锁时重入次数加 1，释放时减 1，减到 0 时真正删除锁。

#### 适用场景

大部分业务场景的首选方案，解决了基础锁的 TTL 超时问题。

### 5.3 Redlock 算法

#### 设计目的

解决 Redis 主从异步复制带来的锁丢失问题：客户端 A 在主节点加锁成功，但锁尚未同步到从节点时主节点宕机，从节点提升为主后，客户端 B 也能加锁成功。

#### 算法流程

1. 部署 N 个独立的 Redis 主节点（通常 N=5）。
2. 客户端依次向每个节点尝试加锁，每次尝试设置较短超时。
3. 若在总超时时间内成功获取 **多数派（N/2+1）** 节点的锁，且剩余有效时间 > 0，则加锁成功。
4. 有效时间 = 原始 TTL - 获取所有锁的总耗时。
5. 若未获取多数派，立即向所有节点发送解锁请求（包括未成功的节点）。

#### 争议与局限

- **Martin Kleppmann 的批评**: 严重依赖有界网络延迟与时钟同步，长 GC 停顿或时钟漂移会破坏正确性。
- **Antirez 的反驳**: 在合理运维和时钟同步下，Redlock 是足够安全的。
- **结论**: 不适合强正确性场景（如资金转账），更适合防重复计算等场景。

### 5.4 ZooKeeper 分布式锁

#### 核心机制

1. 客户端在锁根节点下创建**临时顺序节点**。
2. 判断自己是否为最小节点：
   - 是：获取锁，执行业务逻辑。
   - 否：监听前一个节点的删除事件（Watcher），避免羊群效应。
3. 前一个节点被删除时，重新判断自己是否为最小节点。

#### 优势

| 优势 | 说明 |
|------|------|
| 自动释放 | 会话断开自动清理临时节点，防止死锁 |
| 公平锁 | 按创建顺序排队，天然支持公平锁 |
| 强一致性 | 基于 ZAB 协议，保证强一致性 |
| 无时钟依赖 | 不依赖客户端时钟同步 |

#### 劣势

- 性能不如 Redis（需写磁盘 + 多数派确认）。
- Curator 框架的可重入仅限同一 JVM 内同线程。
- 不建议仅为一把锁引入 ZK，增加系统复杂度。

### 5.5 Fencing Token（隔离令牌）

#### 解决的问题

任何基于租约的锁（包括 Redis 和 ZK）在遭遇网络分区或 GC 停顿时，都会产生一个时间窗口：旧客户端误以为自己仍持有锁，但锁已过期并被新客户端获取。

#### 原理

1. 锁服务在每次成功加锁时返回一个**单调递增的 Token**（如序号）。
2. 客户端在写入资源时携带 Token。
3. 资源端（如 MySQL、对象存储）校验 Token：
   - 若 Token >= 已记录的最大 Token，写入成功并更新记录。
   - 若 Token < 已记录的最大 Token，拒绝写入（陈旧客户端）。

#### 资源端实现示例

```sql
UPDATE account SET balance = ?, fencing_token = ?
WHERE id = ? AND fencing_token < ?
```

#### 定位

所有分布式锁方案的**安全兜底机制**，尤其适用于不可逆的关键业务操作。

### 5.6 分布式锁选型对比

| 维度 | Redis / Redisson | ZooKeeper | etcd |
|------|-----------------|-----------|------|
| 性能 | 极高（内存操作） | 较低（磁盘写入 + 多数派确认） | 中等 |
| 一致性模型 | 尽力而为（AP） | 强一致（CP） | 强一致（CP） |
| 自动释放 | 依赖 TTL + 看门狗 | 会话断开自动清理 | 依赖 TTL + 续约 |
| 公平锁 | 不支持（默认） | 天然支持 | 需额外实现 |
| 时钟依赖 | 依赖 | 不依赖 | 依赖（但影响较小） |
| 适用场景 | 防重复计算、容忍极端并发 | 资金/库存等不可逆操作 | 云原生生态、K8s 环境 |
| 运维成本 | 低 | 高（需独立部署 ZK 集群） | 中等 |

**选型建议**:

- 效率优先、容忍极端并发 -> Redis / Redisson
- 正确性优先、不可逆操作 -> ZK 或 etcd + Fencing Token
- K8s 生态 -> etcd
- 不建议仅为一把锁引入 ZK

## 六、过期删除策略与内存淘汰策略

### 6.1 过期删除策略

#### 三种理论方案对比

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **定时删除** | 设置过期时间时创建定时器，到期自动删除 | 内存友好（及时释放） | CPU 开销大（大量定时器） |
| **惰性删除** | 访问 key 时才检查是否过期，过期则删除 | CPU 友好（无额外计算） | 内存浪费（未访问的过期 key 不会被清理） |
| **定期删除** | 每隔一段时间随机抽查一批 key，删除已过期的 | 折中平衡 | 频率和检查数量难以调优 |

#### Redis 实际方案：惰性删除 + 定期删除

**惰性删除**:

- 每次执行读写命令前，检查涉及的 key 是否过期。
- 若过期则删除，命令返回空或错误。
- 保证被访问的过期 key 一定会被清理。

**定期删除**:

- 默认每秒执行 **10 次**（每 100ms 一次）。
- 每次随机抽取 **20 个**设置了过期时间的 key 进行检查。
- 若超过 **25%** 已过期，继续循环检查下一批。
- 单次执行上限 **25ms**，防止长时间阻塞主线程。
- 若连续循环导致耗时超限，则中止，等待下一轮。

### 6.2 内存淘汰策略（8种）

当内存使用量达到 `maxmemory` 上限时触发淘汰。

#### 仅针对设置了过期时间的 key

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| `volatile-lru` | 淘汰最近最少使用的 key | 缓存场景推荐，保护常驻数据 |
| `volatile-lfu` | 淘汰访问频率最低的 key（4.0+） | 长期热点数据保护 |
| `volatile-ttl` | 淘汰即将过期的 key | 希望尽快清理短期数据 |
| `volatile-random` | 随机淘汰 | 无特殊偏好 |

#### 针对所有 key

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| `allkeys-lru` | 淘汰最近最少使用的 key | 通用缓存场景推荐 |
| `allkeys-lfu` | 淘汰访问频率最低的 key | 需要保护长期热点数据 |
| `allkeys-random` | 随机淘汰 | 无特殊偏好 |

#### 特殊策略

| 策略 | 说明 |
|------|------|
| `noeviction`（默认） | 不淘汰任何数据，内存满时拒绝写入并返回 OOM 错误 |

### 6.3 LRU 与 LFU 实现细节

#### 近似 LRU

- Redis 不维护完整的 LRU 链表（内存开销大），而是采用采样淘汰。
- 对象头中存储最近访问时间戳。
- 淘汰时随机采样 `maxmemory-samples`（默认5）个 key，取访问时间最早的删除。
- 采样数越大，淘汰结果越接近真实 LRU，但 CPU 开销越大。
- **缺陷**: 一次性批量读取（如全量遍历）会"污染"访问时间，导致热点数据被误淘汰。

#### LFU（Redis 4.0+）

- 将对象头的 24bit 拆分为：
  - **16bit**: 访问时间戳（分钟精度，用于衰减）
  - **8bit**: 访问计数器（概率性增长，最大值 255）
- **计数器增长**: 采用对数计数器，访问次数越多，计数器增长概率越低（避免饱和）。
- **时间衰减**: 随时间推移计数器自动衰减，确保淘汰依据是长期访问频率而非短期峰值。
- **优势**: 解决了 LRU 被一次性批量读取污染的问题。

#### 配置建议

```conf
maxmemory 2gb                      # 最大内存限制
maxmemory-policy allkeys-lru       # 淘汰策略
maxmemory-samples 10               # 采样数（越大越精确，默认5）
```

## 七、事务、Lua、Pipeline

### 7.1 Redis 事务

#### 基本命令

```bash
MULTI           # 开始事务，后续命令入队
SET key1 val1   # 命令入队，不立即执行
SET key2 val2   # 命令入队
EXEC            # 顺序执行队列中的所有命令
DISCARD         # 取消事务，清空队列
WATCH key       # 乐观锁，监视 key 的变化
```

#### 执行语义

- `MULTI` 后的命令不会立即执行，而是进入队列。
- `EXEC` 时按入队顺序依次执行，中间不会被其他客户端命令插入。

#### 缺陷

| 缺陷 | 说明 |
|------|------|
| 不支持回滚 | 某条命令执行失败（运行时错误），其余命令仍会继续执行 |
| 不满足原子性 | 与关系型数据库事务语义不同，失败不回滚 |
| 命令入队错误 | 命令语法错误会导致整个事务被拒绝 |
| WATCH 的局限 | 若被监视的 key 在 EXEC 前被修改，事务被取消（需客户端重试） |

**结论**: 日常开发中不推荐使用 Redis 事务。

### 7.2 Lua 脚本

#### 核心优势

| 优势 | 说明 |
|------|------|
| 原子性 | 脚本执行期间不会被其他客户端命令打断 |
| 减少网络开销 | 多条命令一次网络往返 |
| 可复用 | 脚本在服务端缓存，通过 SHA1 值调用 |
| 灵活性 | 支持条件判断、循环等逻辑 |

#### 使用方式

```bash
# 直接执行
EVAL "return redis.call('set', KEYS[1], ARGV[1])" 1 mykey myvalue

# 预加载后通过 SHA1 调用
SCRIPT LOAD "return redis.call('set', KEYS[1], ARGV[1])"
EVALSHA <sha1> 1 mykey myvalue
```

#### 注意事项

- Lua 脚本应尽量简短，避免长时间阻塞主线程（默认超时 5 秒，可通过 `lua-time-limit` 调整）。
- 超时后其他客户端的 `SCRIPT KILL` 可终止脚本，但已开始执行的脚本无法中断。
- 推荐用 Lua 脚本替代 Redis 事务。

### 7.3 Pipeline（管道）

#### 工作原理

客户端将多条命令打包一次性发送给服务端，服务端依次执行后将所有结果打包一次性返回。

```
客户端 -> [CMD1, CMD2, CMD3, ...] -> 服务端
客户端 <- [RES1, RES2, RES3, ...] <- 服务端
```

#### 核心优势

- 减少网络往返次数（RTT），显著提升批量操作性能。
- 例如：1000 条命令，非 Pipeline 需 1000 次 RTT，Pipeline 仅需 1 次 RTT。

#### 与事务的对比

| 维度 | Pipeline | 事务（MULTI/EXEC） |
|------|----------|-------------------|
| 原子性 | 不保证（命令之间可能被插入其他命令） | 保证顺序执行（但不支持回滚） |
| 性能 | 极高（减少 RTT） | 较高（但需额外命令开销） |
| 适用场景 | 批量读写、对原子性无严格要求 | 需要顺序执行的场景 |

#### 注意事项

- 单次 Pipeline 命令数不宜过多（建议不超过 500 条），避免服务端缓冲区溢出。
- Pipeline 不是原子操作，若需要原子性应使用 Lua 脚本。

### 8.1 场景速查表

| 场景 | 推荐方案 | 关键命令/结构 |
|------|---------|--------------|
| 缓存加速 | String + JSON 序列化 | GET / SET |
| 排行榜 | ZSet（score 为分数/时间戳） | ZADD / ZRANGE / ZREVRANGE |
| 计数器/限流 | String INCR 或 Lua 脚本 | INCR / DECR |
| 购物车 | Hash（field 为商品 ID） | HSET / HGET / HDEL |

| 签到统计 | Bitmap | SETBIT / GETBIT / BITCOUNT |
| 页面 UV 统计 | HyperLogLog | PFADD / PFCOUNT |
| 附近的人 | GEO | GEOADD / GEODIST / GEORADIUS |
| 消息队列 | List（阻塞读取） | LPUSH + BRPOP |
| 延迟队列 | ZSet（score 为执行时间戳） | ZADD + ZRANGEBYSCORE（定时轮询） |
| 分布式锁 | Redisson（看门狗自动续期） | SET NX EX + Lua 解锁 |
| 分布式 Session | String / Hash | 多节点共享 Session |

### 8.2 典型场景详解

#### 排行榜

```bash
ZADD leaderboard 100 "player1"
ZADD leaderboard 200 "player2"
ZREVRANGE leaderboard 0 9 WITHSCORES   # Top 10
ZRANK leaderboard "player1"             # 排名
```

#### 延迟队列

```bash
ZADD delay_queue 1700000000 '{"task":"send_email","id":123}'
# 定时轮询
ZRANGEBYSCORE delay_queue 0 1700000000 LIMIT 0 10
# 处理后删除
ZREM delay_queue <task>
```

#### 滑动窗口限流（Lua 脚本）

```lua
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local current = redis.call('GET', key)
if current and tonumber(current) >= limit then
    return 0  -- 拒绝
end
redis.call('INCR', key)
redis.call('EXPIRE', key, window)
return 1  -- 允许
```

## 九、高性能核心原因

### 9.1 为什么 Redis 这么快

| 因素 | 说明 |
|------|------|
| **纯内存操作** | 数据存储在内存中，读写操作均为微秒级 |
| **IO 多路复用** | 基于 Reactor 模式，单线程处理大量并发连接 |
| **单线程模型** | 避免锁竞争和上下文切换开销 |
| **底层数据结构优化** | SDS 预分配、跳表、压缩列表等针对性优化 |
| **高效协议** | RESP 协议简单高效，解析速度快 |

### 9.2 IO 多路复用详解

#### 核心思想

允许单个进程同时监视多个文件描述符（FD），当某个 FD 就绪时进行读写操作。

#### 三种实现对比

| 机制 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **select** | 遍历所有 FD | 跨平台 | FD 数量限制（通常1024）；每次需重新设置；内核遍历开销大 |
| **poll** | 链表存储 FD | 无 FD 数量限制 | 仍需内核遍历；每次需重新设置 |
| **epoll** | 红黑树 + 就绪链表 | 无限制；O(1) 事件通知；支持边缘触发 | 仅 Linux |

#### epoll 工作流程

1. `epoll_create`: 创建 epoll 实例。
2. `epoll_ctl`: 将 FD 注册进内核红黑树，设置关注的事件类型。
3. `epoll_wait`: 阻塞等待事件，就绪的 FD 被放入 ready list。
4. 事件触发时，仅返回就绪的 FD，无需遍历所有 FD。

### 9.3 线程模型演进

| 版本 | 模型 | 说明 |
|------|------|------|
| **6.0 之前** | 完全单线程 | 基于 IO 多路复用，单线程处理所有操作 |
| **6.0+** | 网络 IO 多线程 | 网络读写（read/write）由多线程并行处理，命令执行仍单线程 |
| **原因** | 性能瓶颈不在 CPU | 瓶颈在内存和网络，6.0 前不需要多线程 |

**注意**: 命令执行的单线程保证了命令级别的原子性，无需额外加锁。

## 十、高频面试题精选

### 10.1 基础概念类

**Q: Redis 为什么这么快？**
A: 纯内存操作 + IO 多路复用 + 单线程避免锁竞争 + 底层数据结构优化 + 高效 RESP 协议。

**Q: Redis 单线程还能处理大量并发，为什么？**
A: 基于 IO 多路复用（epoll），单线程可同时监听大量连接。性能瓶颈在网络和内存，不在 CPU。

**Q: Redis 6.0 为什么引入多线程？**
A: 随着网络硬件性能提升，Redis 的性能瓶颈逐渐从内存转向网络 IO。6.0 引入多线程处理网络读写，但命令执行仍为单线程，保证原子性。

**Q: String 和 Hash 存储对象如何选择？**
A: String 适合整体读写、不频繁修改字段的场景；Hash 适合字段频繁修改、需部分读写的场景。大部分场景推荐 String + JSON。

### 10.2 持久化类

**Q: RDB 和 AOF 如何选择？**
A: RDB 恢复快但可能丢数据；AOF 数据安全但恢复慢。推荐混合持久化（RDB 头 + AOF 增量）。主从集群中主节点可关闭落盘，由从节点承担 AOF。

**Q: bgsave 的 fork 过程有什么风险？**
A: fork 操作本身阻塞主进程；COW 机制下高并发写入会导致内存使用量翻倍；必须禁用 THP。

**Q: AOF 重写的过程是怎样的？**
A: fork 子进程根据内存状态生成最小命令集新文件 -> 重写期间增量命令暂存缓冲区 -> 完成后合并缓冲区内容 -> 原子替换旧文件。

### 10.3 高可用类

**Q: 主从复制的全量同步和增量同步有什么区别？**
A: 全量同步：首次连接时生成 RDB 传输 + 缓冲区增量。增量同步：断线重连后根据偏移量从 repl_backlog 获取差异数据。

**Q: 什么是脑裂？如何预防？**
A: 网络分区导致原主节点继续接收写请求，恢复后降级丢失数据。预防：配置 `min-slaves-to-write` 和 `min-slaves-max-lag`。

**Q: Sentinel 如何判断节点故障？**
A: 主观下线：单个 Sentinel 认为不可达。客观下线：法定人数的 Sentinel 均认为不可达，触发故障转移。

### 10.4 缓存设计类

**Q: 缓存穿透、击穿、雪崩的区别？**
A: 穿透：查不存在的数据；击穿：热点 key 过期瞬间并发压力；雪崩：大量 key 同时失效。

**Q: 如何保证缓存与数据库一致性？**
A: 推荐旁路缓存模式（先更新 DB 再删除缓存），删除失败时通过重试机制或消息队列兜底。

**Q: 布隆过滤器的优缺点？**
A: 优点：内存效率高，快速判断元素是否存在。缺点：存在误判率，标准版不支持删除。

### 10.5 分布式锁类

**Q: Redis 分布式锁如何安全释放？**
A: 使用 Lua 脚本，先比较唯一标识再删除，保证原子性，防止误删他人的锁。

**Q: Redisson 看门狗解决了什么问题？**
A: 解决了基础锁 TTL 超时导致锁提前失效的问题。后台线程自动续期，直到业务主动释放。

**Q: Redlock 为什么有争议？**
A: 严重依赖有界网络延迟与时钟同步，GC 停顿或时钟漂移会破坏正确性，不适合强正确性场景。

**Q: Redis 锁和 ZK 锁如何选择？**
A: 效率优先选 Redis/Redisson；正确性优先选 ZK/etcd + Fencing Token。不建议仅为一把锁引入 ZK。

### 10.6 过期与淘汰类

**Q: Redis 的过期删除策略是什么？**
A: 惰性删除（访问时检查）+ 定期删除（每秒10次，每次抽查20个 key，超过25%过期则继续，单次上限25ms）。

**Q: LRU 和 LFU 有什么区别？**
A: LRU 淘汰最近最少访问的 key（可能被一次性批量读取污染）；LFU 淘汰访问频率最低的 key（基于长期访问频率，抗污染）。

**Q: 8 种淘汰策略如何选择？**
A: 缓存场景推荐 `allkeys-lru` 或 `volatile-lru`；需要保护长期热点数据选 LFU 系列；纯缓存可容忍丢失选 `allkeys-random`。
