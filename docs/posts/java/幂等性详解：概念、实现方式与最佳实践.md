## 幂等性详解：概念、实现方式与最佳实践

### 什么是幂等性

幂等性（Idempotency）源自数学概念，其核心定义为：同一操作无论执行一次还是多次，最终产生的业务结果和系统状态都完全一致，不会因重复执行而产生任何副作用。用数学公式表达即为 `f(f(x)) = f(x)`。

在软件工程中，幂等性关注的重点是操作的"最终效果"而非"返回结果"。举例来说，一个创建订单的 API，第一次调用返回 201 并创建了订单，后续相同请求返回 200 并返回已创建的订单信息——虽然 HTTP 响应码不同，但系统状态是一致的（只有一笔订单），这就是幂等的。

### 为什么需要幂等性

在分布式系统中，网络是不可靠的。请求超时、连接中断、服务崩溃等情况随时可能发生，客户端和中间件为了容错往往会进行自动重试。如果没有幂等性保障，重试就可能造成严重的业务问题：

**支付场景**：用户发起支付后网络超时，系统自动重试。若接口不幂等，同一笔交易可能被扣款多次。

**电商下单**：用户点击"提交订单"后页面加载缓慢，反复点击可能产生多笔重复订单，导致重复发货。

**消息消费**：消息队列通常提供 at-least-once 投递保证，消费者必须能够安全地处理重复消息。

**用户注册**：确认页面加载失败时用户可能重复提交表单，导致创建多个重复账号。

这些问题在支付、退款、票务、库存扣减等关键业务场景中尤为严重，直接关系到资金安全和数据一致性。

### HTTP 方法与天然幂等性

HTTP 协议本身对方法的幂等性有明确的语义约定：

GET、HEAD、OPTIONS 等查询方法是天然幂等的——读取数据不会改变系统状态，多次调用效果相同。

PUT 和 DELETE 在设计上也是幂等的。PUT 要求客户端提交完整的资源表示来覆盖目标资源，无论执行多少次，最终状态都一样；DELETE 删除一个资源后，再次删除只是返回"资源不存在"，系统状态不变。

POST 则不同——它通常用于创建资源或触发副作用，每次调用可能产生不同的结果。因此，POST 接口是需要工程师主动设计幂等性保障的主要对象。

值得注意的是，"天然幂等"依赖于正确的实现。如果一个 GET 请求意外地修改了数据库计数器，那它就不再幂等了。PUT 如果实现为"在原值基础上加 10"（`SET price = price + 10`）而非"设为指定值"（`SET price = 90`），也会丧失幂等性。

### 幂等性的实现方式

以下按适用场景和复杂度，梳理主流的幂等性实现方案。

#### 一、幂等性密钥（Idempotency Key）

这是目前业界最通用、最成熟的方案，被 Stripe、AWS 等主流服务广泛采用。

其核心思路是：客户端为每一个"逻辑操作"生成一个全局唯一的标识符（通常是 UUID），放在请求头（如 `Idempotency-Key`）中发送给服务端。服务端收到请求后，先检查这个 Key 是否已经被处理过：

- 如果 Key 不存在，说明是首次请求，执行业务逻辑并将 Key 与处理结果关联存储。
- 如果 Key 已存在且处理完成，直接返回缓存的结果，不再执行任何副作用。
- 如果 Key 已存在但处理正在进行中，则返回 409 Conflict 或 202 Accepted 让客户端轮询。

**关键设计要点**：

幂等性 Key 必须由客户端生成并在重试时保持一致，不能由服务端在收到请求后才分配。Key 需要绑定请求体（通常计算请求的 hash），防止同一个 Key 被用于不同的请求内容。Stripe 的做法是：服务端存储 Key 对应的请求 hash，如果后续重试的 Key 相同但请求体 hash 不匹配，会返回错误提醒客户端修复 bug。

**存储与生命周期**：

幂等性记录需要持久化存储（数据库或 Redis），包含 Key、请求 hash、处理状态、响应缓存、过期时间等字段。记录的保留时间应覆盖实际可能的重试窗口（通常为数小时到数天）。过期后应清理，避免存储无限膨胀。

#### 二、数据库唯一约束

适用于以插入操作为主的场景。

通过在数据库表中添加唯一索引（Unique Index），利用数据库自身的能力来拒绝重复数据。当重复插入触发唯一键冲突异常时，服务端捕获该异常并返回成功响应（附带已存在的记录）。

在分布式环境中，推荐使用全局唯一 ID（如 Snowflake 算法生成的 ID）作为唯一键，而非依赖数据库自增主键。Snowflake 利用时间戳、机器标识和序列号的组合，能在高吞吐场景下保证全局唯一性。

此外，MySQL 的 `INSERT IGNORE` 和 `INSERT ... ON DUPLICATE KEY UPDATE` 也是基于唯一约束的变体写法，可以在一条 SQL 中完成"存在则跳过/更新，不存在则插入"的逻辑。

#### 三、乐观锁

适用于以更新操作为主的场景。

在数据表中增加一个 `version` 字段，每次更新时将 version 值加 1。客户端在更新前需要先读取当前版本号，更新时以版本号作为条件：

```sql
UPDATE orders SET price = 80, version = version + 1
WHERE id = 1 AND version = 3;
```

如果受影响行数为 0，说明数据已被其他操作修改，当前更新失败。这种方式能有效解决"ABA 问题"——即一个延迟到达的旧请求覆盖了已经被更新过的新数据。

乐观锁适合读多写少、并发冲突概率低的场景。在高冲突场景下，大量更新会因版本号不匹配而失败，需要客户端频繁重试，反而降低系统吞吐量。

#### 四、状态机

适用于有明确业务流程的场景，如订单流转、审批流、支付流程等。

通过定义有限的状态集合和合法的状态迁移路径，从根本上阻止非法的重复操作。例如一个订单的状态流转为：`待支付 → 已支付 → 已发货 → 已完成`。如果订单已经处于"已支付"状态，再次收到支付回调时，系统检查当前状态后会直接忽略，因为 `已支付 → 已支付` 不是合法的迁移。

状态机的优势在于它天然贴合业务语义，实现直观且易于维护。但它的局限在于需要预先明确定义所有状态和迁移路径，不适合状态复杂或动态变化的场景。

#### 五、分布式锁

适用于高并发、需要严格防止并发重复执行的场景。

利用 Redis（SETNX + TTL）或 ZooKeeper 等分布式协调服务，在执行业务操作前先获取锁。获取到锁的节点执行操作，其他节点则等待或放弃。这样可以确保同一时刻只有一个请求能进入临界区。

需要注意的几个问题：锁必须设置过期时间，防止持有锁的节点崩溃后锁永远不释放；锁的粒度要合理设计，比如按商品 ID 加锁而非全局加锁，以减小对并发的影响；在极端场景下，Redis 主从切换可能丢失锁，需要评估是否使用 Redlock 等多节点方案。

#### 六、Token 机制

适用于前端表单防重复提交的场景。

服务端在渲染表单页面前生成一个一次性 Token，存入 Redis 并随页面下发给客户端。用户提交表单时，Token 随请求一起发送。服务端收到后检查 Redis 中该 Token 是否存在：存在则删除 Token 并执行业务逻辑；不存在则说明是重复提交，直接拒绝。

这种机制的核心在于 Token 的"原子性检查与删除"——必须保证检查和删除是一个不可分割的操作（Redis 的 `DEL` 命令天然满足），否则在并发场景下仍可能出现两个请求同时通过检查的情况。

#### 七、PRG 模式（Post/Redirect/Get）

一种经典的 Web 应用防重复提交模式。

当用户通过 POST 提交表单后，服务端不直接返回结果页面，而是返回一个 302 重定向响应，让浏览器对另一个 URL 发起 GET 请求来获取结果页。这样，用户刷新页面时重复的是 GET 请求（天然幂等），而非原始的 POST 请求。

PRG 模式实现简单，无需额外的存储或标识机制，但它只解决了"用户刷新页面导致的重复提交"这一个问题，无法应对网络超时重试、程序自动重试等情况。

#### 八、幂等 SQL 设计

在数据库层面直接编写天然幂等的 SQL 语句。

将"增量式"写法改为"绝对值"写法。例如，将 `UPDATE account SET balance = balance - 100 WHERE id = 1`（每次执行余额都会减少）改为 `UPDATE account SET balance = 90 WHERE id = 1`（无论执行多少次，余额都是 90）。当然，这种方式需要在上层先计算出目标值，且只适用于可以直接设定绝对值的场景。

### 不同场景的方案选择

实际工程中，不同业务场景应选择不同的幂等性方案：

前端表单提交适合使用 Token 机制或幂等性密钥，由前端生成 UUID 随表单一起提交，后端进行去重。

第三方回调（如支付回调通知）适合使用业务唯一标识（如商户订单号）配合状态查询，根据回调中的业务 ID 判断是否已处理过。

消息队列消费适合使用消息 ID 或业务 ID 配合数据库唯一约束或已处理消息表，消费者在本地维护一张 `processed_messages` 表，以消息 ID 作为唯一键。

高并发库存扣减适合使用乐观锁（低冲突场景）或分布式锁（高一致性要求场景），并优化锁粒度到商品级别。

分布式事务中的 TCC、SAGA 等模式要求每一个阶段的操作都必须是幂等的，因为框架会自动对失败的阶段进行重试。通常需要在每个参与方同时使用状态机、数据库约束和幂等性密钥等多种手段。

### 电商场景的幂等性设计

电商系统是幂等性设计最典型也最复杂的落地场景，从用户点击"提交订单"到最终收货完成，整条链路上的每个环节都面临重复请求的风险。

#### 订单创建

用户提交订单时可能因网络延迟反复点击"确认下单"按钮，也可能因为前端页面刷新触发重复的 POST 请求。如果不做幂等控制，同一批商品可能被创建出多笔订单。

实践中通常采用"前端 Token + 后端唯一约束"的双重保障。前端在用户进入下单页时向服务端请求一个一次性 Token（存入 Redis），提交订单时携带该 Token；后端收到后先校验并删除 Token，再以订单维度的业务唯一键（如 `用户ID + 商品ID + 时间窗口` 的组合，或服务端生成的全局唯一订单号）作为数据库唯一索引。这样即使 Token 校验被并发穿透，数据库层的唯一约束依然能兜底，防止产生重复订单。

需要注意的是，前端禁用按钮只是辅助手段，无法阻止技术用户绕过 UI 直接调用 API，后端校验才是根本保障。

#### 支付扣款

支付是电商系统中对幂等性要求最严格的环节——重复扣款直接造成资金损失和用户信任危机，是不可触碰的红线。

支付幂等的核心设计分为三层：

第一层是幂等性密钥。客户端发起支付请求时携带唯一的 `ClientToken`（如订单号），支付网关在处理前先检查该 Token 是否已关联过成功的支付结果。如果已存在，直接返回上次的支付结果，不再执行扣款逻辑。

第二层是数据库流水表。在支付流水表中以 `交易单号` 作为唯一索引，每次扣款前先插入一条流水记录。如果插入失败（唯一键冲突），说明该笔交易已被处理过，直接返回。关键要求是：流水记录的插入和实际扣款操作必须在同一个数据库事务中，否则可能出现"流水写了但款没扣"或"款扣了但流水没写"的不一致。

第三层是状态查询兜底。在调用下游支付渠道（如银行、第三方支付）之前，先查询该笔交易的状态。如果渠道侧已返回成功，则本地直接标记为已支付，不再重复发起扣款请求。

对于跨地域的多活部署，还需要解决幂等性记录的跨数据中心同步问题——要么使用全局唯一 ID 服务，要么在每个数据中心独立维护幂等表并定期对齐。

#### 库存扣减

库存扣减面临的核心挑战是高并发下的"超卖"和"少卖"问题。传统的增量式 SQL（`UPDATE stock SET amount = amount - 1 WHERE goods_id = 1`）既不幂等也不能防止并发超卖。

常见的解决思路有两种：

乐观锁 + 条件更新。将扣减 SQL 改为 `UPDATE stock SET amount = amount - #{num} WHERE goods_id = #{goodsId} AND amount - #{num} >= 0`。这样即使同一个扣减请求被重复执行，第一次扣减成功后库存值已经变化，第二次执行时 `amount - #{num} >= 0` 的条件不再满足（或者版本号已变），受影响行数为 0，系统可以据此判断为重复操作并跳过。

预扣减 + 状态确认。先在 Redis 中用 Lua 脚本原子性地执行库存预扣减，成功后再异步写入数据库。由于 Lua 脚本在 Redis 中是原子执行的，天然避免了并发问题；同时通过业务唯一键（如订单号）记录预扣减状态，重复请求到来时查询状态即可判断是否已扣减过。

#### 退款

退款操作同样需要严格的幂等保障——重复退款意味着平台多退了钱。退款的幂等设计通常依赖"退款单号"作为业务唯一标识：每笔退款对应一个全局唯一的退款单号，在退款表中设置唯一索引。发起退款时先插入退款记录（触发唯一约束即视为重复），再执行实际的退款操作。同时配合状态机，只有处于"待退款"状态的退款单才能被处理，"已退款"或"退款失败"状态的重复请求会被直接忽略。

#### 物流发货

发货环节的重复请求可能来自上游订单系统的重试或运营人员的重复操作。幂等控制通常基于订单号做唯一约束——一个订单只能生成一条发货单，重复的发货请求会被数据库唯一索引拦截。同时配合状态机，只有"已支付"状态的订单才能触发发货，"已发货"或"已签收"状态的重复请求直接返回。

### 常见陷阱与最佳实践

**常见陷阱**：

客户端每次重试都生成新的幂等性 Key，导致服务端无法识别重复请求。这通常是因为客户端在构造请求时使用了 `UUID.randomUUID()` 而没有缓存第一次生成的值。

同一个幂等性 Key 被用于不同的请求内容，导致服务端返回错误的缓存结果。

仅依赖内存中的去重记录。单机内存不共享且进程重启后丢失，在分布式环境和故障恢复场景下完全失效。

在获取幂等性锁之前就触发了外部副作用（如已经调用了第三方支付接口），一旦锁定失败，副作用已经无法回滚。

将幂等性与"恰好一次"（exactly-once）语义混淆。幂等性保证的是"多次执行结果一致"，而不是"只执行一次"。操作可能实际执行了多次，但只要最终状态一致就是幂等的。

**最佳实践**：

对所有会触发副作用的 API 端点强制要求幂等性 Key，并在 API 文档中明确说明。

将幂等性记录的写入和业务数据的变更放在同一个数据库事务中，确保两者要么同时成功，要么同时失败。

在重试时使用指数退避（Exponential Backoff）策略，等待时间为 `2^n`（n 为失败次数），并加入随机抖动（Jitter），避免大量客户端同时重试造成"惊群效应"压垮服务端。Stripe 的官方 SDK 就内置了这一机制。

为幂等性记录设置合理的过期时间，既要覆盖实际可能的重试窗口，又不能无限保留占用存储。

通过并发重试、进程崩溃恢复、下游服务超时等场景进行充分的幂等性测试。

查询类接口天然幂等，无需额外处理——把精力集中在状态变更类接口上即可。

### 面试高频问题与回答思路

幂等性是后端和系统设计面试中的高频话题，尤其在涉及支付、电商、分布式系统的岗位面试中几乎必考。以下梳理常见问题及推荐的回答思路。

#### Q1：什么是幂等性？为什么需要幂等性？

**回答思路**：先给出数学定义 `f(f(x)) = f(x)`，再翻译成工程语言——同一操作执行一次和执行多次的系统状态完全一致。然后说明为什么需要：分布式系统中网络不可靠是常态，超时重试、消息重复投递、用户重复点击都会导致操作被多次执行，如果没有幂等保障，就会出现重复扣款、重复下单、数据不一致等严重问题。建议举一个支付场景的具体例子。

#### Q2：HTTP 的哪些方法是幂等的？

**回答思路**：GET、HEAD、OPTIONS、TRACE 是天然幂等的查询方法；PUT 和 DELETE 在设计上也是幂等的（PUT 是全量覆盖，DELETE 是删除资源）；POST 不幂等，因为它通常用于创建资源，每次调用可能产生新的资源。关键点是要补充说明"天然幂等"依赖正确的实现，比如 PUT 如果实现为 `price = price + 10` 就不再幂等了，需要改为 `price = 90` 这种绝对值赋值。

#### Q3：接口幂等性的常见实现方案有哪些？

**回答思路**：按照从简单到复杂的顺序列举——幂等性密钥（Idempotency Key）、数据库唯一约束、乐观锁（版本号）、状态机、分布式锁、Token 机制、PRG 模式、幂等 SQL。对每种方案简要说明适用场景，面试官通常会追问其中 2-3 种的实现细节和优缺点对比。

#### Q4：设计一个支付接口的幂等方案？

**回答思路**：这是最经典的场景题。建议按分层思路回答：客户端生成唯一的 `ClientToken` 随请求发送；服务端用防重表（以交易单号为唯一索引）做第一道拦截；扣款操作和防重记录在同一个数据库事务中保证一致性；调用支付渠道前先查询交易状态做兜底。如果面试官追问分布式场景，再补充跨数据中心的幂等记录同步问题。

#### Q5：分布式锁能解决幂等问题吗？

**回答思路**：这道题考察对分布式锁定位的理解。正确回答是：分布式锁只能防并发（同一时刻只有一个请求进入临界区），但不能根本性地解决幂等问题。如果第一个请求处理完释放了锁，第二个相同请求到达时又能获取到锁并再次执行。分布式锁是"防并发"的手段，真正的幂等还需要配合数据库唯一约束或业务状态判断来实现。面试中能指出这个区别会是一个加分项。

#### Q6：幂等和"恰好一次"（Exactly-Once）有什么区别？

**回答思路**：幂等性保证的是"多次执行结果一致"，操作可能实际执行了多次，但最终状态等同于只执行了一次。Exactly-Once 保证的是操作只被执行一次，这在分布式系统中几乎不可能实现（因为网络分区、节点故障等因素不可控）。实际工程中，大多数系统选择 At-Least-Once 投递 + 幂等消费的组合来模拟 Exactly-Once 的语义，这比追求真正的 Exactly-Once 更务实也更可靠。

#### Q7：防重表和业务表不在同一个数据库怎么办？

**回答思路**：理想情况下防重表和业务表应该在同一个数据库，这样可以在同一个事务中保证原子性。如果确实分开了（比如分库分表场景），可以引入本地消息表或事务消息来保证最终一致性：先在本地数据库写入一条"处理记录"，再通过异步消息触发业务操作，消费端通过幂等消费来保证最终只处理一次。也可以利用 TCC 等分布式事务框架来协调跨库操作。

#### Q8：消息队列消费端如何保证幂等？

**回答思路**：消息队列通常提供 At-Least-Once 投递保证，意味着同一条消息可能被消费多次。消费端幂等的常见做法有两种：一是维护一张 `processed_messages` 表，以消息 ID 作为唯一键，消费前先插入，成功才处理业务逻辑；二是利用业务天然唯一键（如订单号），在业务表中设置唯一约束，重复消费时数据库层直接拦截。面试官可能会追问"先写消息记录还是先执行业务逻辑"，正确答案是两者必须在同一个事务中完成。

#### Q9：如何测试幂等性？

**回答思路**：幂等性测试需要覆盖多种异常场景——模拟客户端并发发送相同请求、在业务执行中途杀掉进程（模拟崩溃恢复）、模拟下游服务超时后触发重试、模拟 Redis/数据库故障后的恢复过程。验证的标准是：无论发生何种重试，数据库中的业务数据与只执行一次的结果完全一致。如果能提到使用 Chaos Engineering 工具进行故障注入测试会是加分项。

#### Q10：高并发场景下幂等方案的性能如何优化？

**回答思路**：可以从几个层面优化——缓存层前置，先用 Redis 快速过滤已处理的请求，避免每次都查数据库；缩小锁粒度，按业务 ID（如商品 ID）加锁而非全局加锁，减少锁竞争；异步化非关键路径，将通知、日志等非核心操作从主流程中剥离；设置合理的幂等记录过期时间，定期清理过期数据，避免存储膨胀影响查询性能。如果面试官追问极端场景，可以提到本地缓存 + Redis + 数据库三级过滤的架构。

### 总结

幂等性是构建可靠分布式系统的基础保障之一。它不是一个单一的技术方案，而是一种贯穿系统设计始终的工程思维。在实际落地时，往往需要根据具体的业务场景、并发水平和一致性要求，组合使用多种实现方式——幂等性密钥提供通用的请求级去重，数据库唯一约束兜底数据层的一致性，状态机保障业务流程的正确性，乐观锁和分布式锁解决并发冲突。理解每种方案的适用场景和局限性，才能设计出既安全又高效的幂等性策略。
