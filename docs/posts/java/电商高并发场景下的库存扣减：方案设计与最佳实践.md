## 电商高并发场景下的库存扣减：方案设计与最佳实践

在电商系统中，库存扣减是最核心也最容易出问题的环节之一。当促销活动或秒杀场景下瞬时涌入大量请求时，系统必须同时解决三个矛盾：并发安全（不能超卖）、数据一致（不能少卖）、以及系统性能（不能被打垮）。本文从问题本质出发，逐层剖析从数据库到缓存、从同步到异步的各种方案，给出可落地的最佳实践。

---

### 一、核心挑战

库存扣减本质上是一个"读-判断-写"的复合操作：先读取当前库存，判断是否满足购买数量，然后执行扣减。在并发环境下，这三个步骤之间存在时间窗口，多个请求可能同时读到相同的库存值并各自扣减，最终导致库存变为负数——这就是所谓的"超卖"。

与之对应的是"少卖"问题：为了防止超卖而采取的过于保守的策略（如扣减失败即放弃），可能导致明明有库存却卖不出去。在秒杀场景中，由于大量请求几乎同时到达，少卖的概率并不低。

此外还有两个隐性挑战：一是性能瓶颈，数据库行级锁在高并发下会导致大量线程阻塞甚至死锁；二是分布式环境下的数据一致性，库存服务、订单服务、支付服务往往是独立的微服务，任何一个环节失败都需要可靠的回滚机制。

### 二、数据库层方案

#### 2.1 悲观锁

最直接的方式是在事务中使用 `SELECT ... FOR UPDATE` 对库存行加排他锁：

```sql
BEGIN;
SELECT stock FROM product_inventory WHERE product_id = 1001 FOR UPDATE;
-- 应用层判断 stock >= quantity
UPDATE product_inventory SET stock = stock - 1 WHERE product_id = 1001;
COMMIT;
```

这种方式能保证强一致性，但代价极大。排他锁会让所有并发请求串行化，数据库连接池被快速耗尽，吞吐量急剧下降。更严重的是，如果事务中还涉及其他表的写操作，容易引发死锁。因此悲观锁仅适用于并发量较低（百级 QPS 以下）的场景，秒杀和大促场景下基本不可用。

#### 2.2 乐观锁（版本号机制）

乐观锁不阻塞读操作，而是在更新时通过版本号或时间戳校验数据是否被修改过：

```sql
-- 读取时同时获取版本号
SELECT stock, version FROM product_inventory WHERE product_id = 1001;

-- 更新时校验版本号
UPDATE product_inventory
SET stock = stock - 1, version = version + 1
WHERE product_id = 1001 AND version = #{oldVersion};
```

如果 `version` 已被其他事务修改，`UPDATE` 影响行数为 0，应用层需要重试。这种方式在低并发下表现良好，但在秒杀场景中，大量请求几乎同时读到相同版本号，只有极少数能更新成功，其余全部失败重试——形成"自旋"效应，数据库依然承受巨大压力。乐观锁适合并发冲突概率不高（<20%）的业务场景。

#### 2.3 CAS 条件更新（推荐的基础方案）

相比乐观锁的版本号机制，基于条件判断的 CAS（Compare-And-Swap）更加简洁高效：

```sql
UPDATE product_inventory
SET stock = stock - #{quantity}
WHERE product_id = 1001 AND stock >= #{quantity};
```

这条语句利用数据库本身的行级锁和原子性，将"判断库存是否充足"和"执行扣减"合并为一次操作。如果返回影响行数为 0，说明库存不足，直接失败即可，无需重试。这是数据库层面最推荐的库存扣减方式，也是所有上层方案的最终兜底手段。

但 CAS 方案仍然存在瓶颈：高并发下对同一行的大量 `UPDATE` 操作会导致行锁竞争严重，MySQL 单行锁的吞吐量大约在 1000~3000 QPS，无法满足万级并发的秒杀需求。

### 三、Redis 缓存层方案

为了突破数据库的性能瓶颈，业界的主流做法是将库存预加载到 Redis 中，由缓存层承担绝大部分的扣减请求，数据库只做最终落库。

#### 3.1 Redis 预扣减 + Lua 原子脚本

Redis 执行 Lua 脚本时保证原子性——脚本中的所有命令作为一个整体执行，不会被其他命令插入。利用这个特性，可以将"查库存-判断-扣减"三步操作封装为一个 Lua 脚本：

```lua
-- KEYS[1]: 库存key, ARGV[1]: 扣减数量
local stock = tonumber(redis.call('GET', KEYS[1]))
local quantity = tonumber(ARGV[1])

if stock == nil then
    return -1  -- 库存key不存在
end

if stock < quantity then
    return -2  -- 库存不足
end

local newStock = redis.call('DECRBY', KEYS[1], quantity)
if newStock >= 0 then
    return newStock  -- 扣减成功，返回剩余库存
else
    -- 极端情况下（如并发DECRBY）扣减后为负，回滚
    redis.call('INCRBY', KEYS[1], quantity)
    return -3
end
```

Spring Boot 集成调用示例：

```java
@Service
public class InventoryService {
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    @Autowired
    private DefaultRedisScript<Long> deductStockScript;

    public long deductStock(String productId, int quantity) {
        String key = "stock:" + productId;
        Long result = redisTemplate.execute(
            deductStockScript,
            Collections.singletonList(key),
            String.valueOf(quantity)
        );
        return result;  // >= 0: 剩余库存; < 0: 扣减失败
    }
}
```

这是目前业界最广泛采用的防超卖方案。Redis 单节点执行 Lua 脚本的吞吐量可达数万 QPS，相比数据库有数量级的提升。

#### 3.2 分布式锁方案

另一种思路是通过 Redis 分布式锁（如 Redisson、SETNX）对库存操作加互斥锁：

```java
// Redisson 分布式锁
RLock lock = redisson.getLock("lock:stock:" + productId);
try {
    if (lock.tryLock(3, 10, TimeUnit.SECONDS)) {
        // 加锁成功后执行扣减逻辑
        int stock = getStock(productId);
        if (stock >= quantity) {
            deductStock(productId, quantity);
            return true;
        }
    }
    return false;
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

分布式锁能保证安全性，但本质是将并发操作串行化，吞吐量受限于锁的粒度和持有时间。对于秒杀这种极端并发场景，分布式锁的性能远不如 Lua 脚本方案。分布式锁更适合用在库存补充、运营后台修改库存等低频写入场景，防止与扣减操作产生并发冲突。

**锁续命与 RedLock**：如果业务执行时间可能超过锁的过期时间，需要引入 Watchdog 机制自动续期。在 Redis 集群环境下，主从切换可能导致锁丢失，可以考虑 RedLock 算法（向 5 个独立 Redis 实例申请锁，超过半数成功即视为获锁），但 RedLock 的实现复杂度和运维成本较高，大多数场景用单实例 Redis 锁 + Lua 脚本即可满足需求。

#### 3.3 库存分片（热点 Key 打散）

当单个商品的库存 key 成为热点（例如千万级用户抢同一件商品），即使 Redis 单节点也可能成为瓶颈。借鉴 `ConcurrentHashMap` 的分段锁思想，可以将库存拆分为多个分片：

```java
// 初始化：将 10000 件库存拆为 10 段
public void initSegmentStock(String productId, int totalStock, int segments) {
    int base = totalStock / segments;
    for (int i = 0; i < segments; i++) {
        int segStock = (i == segments - 1)
            ? base + totalStock % segments
            : base;
        redisTemplate.opsForValue()
            .set("stock:" + productId + ":" + i, String.valueOf(segStock));
    }
}

// 扣减时随机选择分片，失败则轮询下一个
public boolean segmentDeduct(String productId, int quantity) {
    int segments = getSegmentCount(productId);
    int startIndex = ThreadLocalRandom.current().nextInt(segments);
    for (int i = 0; i < segments; i++) {
        int idx = (startIndex + i) % segments;
        String key = "stock:" + productId + ":" + idx;
        Long result = redisTemplate.execute(
            deductStockScript, Collections.singletonList(key),
            String.valueOf(quantity));
        if (result != null && result >= 0) return true;
    }
    return false;  // 所有分片均不足
}
```

分片方案将热点 key 分散到 Redis Cluster 的不同节点上，理论上可以线性扩展吞吐量。但需要配合定时任务合并"碎片"——当某些分片库存耗尽而其他分片还有余量时，需要合并以保证整体可售。

### 四、消息队列与异步处理

仅靠 Redis 预扣减并不能完成完整的交易流程。预扣减成功后还需要创建订单、实际扣减数据库库存、发起支付，这些步骤如果全部同步执行，响应时间会很长，且任意环节失败都会导致数据不一致。

#### 4.1 异步削峰

将预扣减成功的请求投递到消息队列（如 RocketMQ、Kafka），由后端的订单服务和库存服务按自身能力消费处理。这样做有两个好处：一是将瞬时流量峰值削平，保护下游数据库；二是解耦各服务，提高系统整体弹性。

```
用户请求 → Redis Lua 预扣减 → 成功 → 发送 MQ 消息 → 立即返回"排队中"
                                                    ↓
                              订单服务消费 → 创建订单 → DB 库存扣减(CAS) → 成功 → 通知用户
```

#### 4.2 事务消息保证最终一致性

在分布式环境下，"预扣库存成功但订单创建失败"或"订单创建成功但库存扣减失败"都是可能出现的情况。RocketMQ 的事务消息机制可以解决本地事务与消息发送的原子性问题：

```java
// 1. 发送半消息（half message，消费者不可见）
mqProducer.sendMessageInTransaction(msg, (message, arg) -> {
    // 2. 执行本地事务（如创建订单）
    boolean success = orderService.createOrder(orderId, productId, quantity);
    if (success) {
        // 3. 本地事务成功，提交消息
        return LocalTransactionState.COMMIT_MESSAGE;
    } else {
        // 4. 本地事务失败，回滚消息
        return LocalTransactionState.ROLLBACK_MESSAGE;
    }
    return LocalTransactionState.UNKNOW;  // 异常情况，由 broker 回查
});
```

对于不支持事务消息的 MQ，可以采用"本地消息表 + 定时补偿"的方案：在业务数据库中建一张消息表，与业务操作在同一个本地事务中写入，再由定时任务扫描未发送的消息投递到 MQ。

#### 4.3 异步补偿防少卖

消息队列方案中可能出现的异常场景包括：Redis 预扣成功但 MQ 消息丢失、消费者处理失败但重试耗尽等。这些情况会导致"少卖"——Redis 中库存已扣但实际没有生成订单。

解决方案是建立多层补偿机制：

第一层是 MQ 消费失败后的自动重试（RocketMQ 默认重试 16 次，间隔递增）。第二层是定时任务对账：每隔几分钟扫描 Redis 中的已售数量与数据库中的实际订单数量，如果 Redis 已售数量大于数据库订单数量，说明存在少卖，将差值回补到 Redis。第三层是每日凌晨低峰期的全量校准，以数据库为准重置 Redis 库存。

### 五、库存回滚与补偿机制

在完整的交易链路中，库存"扣了又需要还回去"的场景非常常见：用户下单后未支付导致订单超时取消、支付失败、用户主动退款、风控拦截等。回滚机制的设计直接影响系统的数据准确性和用户体验。

#### 5.1 订单超时回滚

最常见的做法是在创建订单时设置一个过期时间（如 15 分钟或 30 分钟），到期未支付则自动取消并回补库存。实现方式有三种：

**延迟队列**：订单创建后发送一条延迟消息到 MQ（RocketMQ 支持精确的延迟级别），到期后消费者检查订单状态，若未支付则执行取消和库存回补。

```java
// 发送延迟消息
Message msg = new Message("ORDER_TIMEOUT", orderId.getBytes());
msg.setDelayTimeLevel(14);  // 对应 30 分钟延迟
mqProducer.send(msg);

// 消费者处理
@RocketMQMessageListener(topic = "ORDER_TIMEOUT", ...)
public class OrderTimeoutConsumer implements RocketMQListener<String> {
    public void onMessage(String orderId) {
        Order order = orderService.getOrder(orderId);
        if (order.getStatus() == UNPAID) {
            orderService.cancelOrder(orderId);
            // 回补 Redis 库存
            inventoryService.rollbackStock(order.getProductId(), order.getQuantity());
            // 回补数据库库存
            inventoryService.rollbackDbStock(order.getProductId(), order.getQuantity());
        }
    }
}
```

**Redis Key 过期通知**：利用 Redis 的 keyspace notification 机制，为订单设置 TTL，过期时触发回调。但这种方式在生产环境中可靠性不高（Redis 不保证过期通知的及时性和必达性），仅适合对可靠性要求不高的场景。

**定时任务扫描**：每隔一定周期（如 1 分钟）扫描订单表中已超时的未支付订单，批量执行取消和回补。实现简单但有延迟，适合对时效性要求不高的业务。

#### 5.2 回滚操作的一致性

库存回滚同样需要同时操作 Redis 和数据库，存在一致性风险。推荐的做法是：

先回补数据库库存（CAS 方式防止重复回补），成功后再回补 Redis。如果 Redis 回补失败，由补偿任务兜底。关键是回补操作必须是幂等的——同一笔订单无论回补多少次，结果都应该一致。可以通过"库存流水表"记录每一笔扣减和回补操作，用订单号作为幂等键：

```sql
-- 扣减时记录流水
INSERT INTO inventory_log (order_id, product_id, change_type, quantity, created_at)
VALUES (#{orderId}, #{productId}, 'DEDUCT', #{quantity}, NOW());

-- 回补时先检查是否已回补过（幂等校验）
SELECT COUNT(*) FROM inventory_log
WHERE order_id = #{orderId} AND change_type = 'ROLLBACK';

-- 未回补过才执行
INSERT INTO inventory_log (order_id, product_id, change_type, quantity, created_at)
VALUES (#{orderId}, #{productId}, 'ROLLBACK', #{quantity}, NOW());

UPDATE product_inventory
SET stock = stock + #{quantity}
WHERE product_id = #{productId};
```

### 六、缓存与数据库库存一致性

Redis 预扣减方案将库存判断前置到了缓存层，但这引入了一个经典问题：Redis 中的库存数据与数据库中的实际库存如何保持一致？不一致会导致两类故障——Redis 库存偏少（少卖，用户买不到）或 Redis 库存偏多（超卖，卖出后 DB 扣减失败）。

需要特别强调的是，秒杀/大促场景与普通电商场景在一致性策略上存在本质区别。普通场景的库存 key 允许删除和重建，而秒杀场景的 Redis 库存 key 绝对不能删除。

#### 6.1 为什么秒杀场景不能删缓存

在普通电商场景中，库存 key 的访问频率相对平稳，可以采用经典的 Cache-Aside 模式——更新数据库后删除缓存，下次读取时从数据库重新加载。但在秒杀场景下，这种做法会直接导致系统崩溃：

**缓存击穿**：如果删除 Redis 库存 key，下一瞬间涌入的数万并发请求会发现缓存未命中，全部穿透到数据库执行 `SELECT ... FOR UPDATE` 或 `UPDATE ... WHERE stock >= N`。MySQL 单行锁的吞吐量仅约 1000~3000 QPS，而秒杀流量通常是万级甚至十万级 QPS，数据库连接池会在毫秒内被耗尽，导致整个交易系统雪崩。

**写缓冲失效**：秒杀场景中 Redis 库存 key 的角色不是传统意义上的"缓存"（读多写少的数据副本），而是一个"写缓冲"（Write Shield）——它的首要职责是吸收海量写请求，保护数据库不被打垮。删除写缓冲等于主动拆掉了数据库前面的防波堤。

**回填数据不准**：即使删缓存后立即从数据库重新加载库存值，这个值也可能已经过时——在加载的瞬间，可能又有数百个扣减请求正在处理中。回填的库存值偏大，会导致后续扣减基于错误的高库存值执行，最终引发超卖。

因此，秒杀场景下 Redis 库存 key 的生命周期应该是：活动开始前预热写入 → 活动期间只做原子读写（Lua 脚本）→ 活动结束后才清理或重置。整个活动期间，这个 key 绝对不能被删除。

#### 6.2 秒杀场景的正确一致性策略：不删缓存，只同步修正

既然不能删缓存，那就只能在 Redis 上做原地修正。秒杀库存的一致性策略从"删缓存让 DB 重新加载"转变为"Redis 是实时权威，DB 异步追认，后台持续校准"。

**Write-Through 模式（Redis 写穿）**：所有库存变更都以 Redis 为准进行实时判断，变更事件异步写入数据库。这与 Cache-Aside 的"先写 DB 再更新缓存"方向完全相反——Redis 是写入的第一站，DB 是最终持久化的终点。

```
用户请求 → Redis Lua 原子扣减（实时判断）
                │
                ├── 扣减成功 → 发送 MQ 消息 → 订单服务 → DB 库存扣减（CAS 兜底）
                │
                └── 扣减失败 → 直接返回"库存不足"（请求不过DB）
```

在这个架构中，Redis 和 DB 之间的数据流是单向的：Redis → MQ → DB。不存在"DB 写完再去更新 Redis"的环节，因此也就没有"删缓存"的需求。

#### 6.3 不一致的来源与逐层修正

即使采用 Write-Through 模式，Redis 和 DB 之间仍然可能出现不一致。来源有三类：

**MQ 消息丢失或消费失败**：Redis 扣减成功，但 MQ 消息未到达或消费者处理失败，导致 DB 中库存未扣、订单未创建。这会造成"少卖"——Redis 显示已售出但实际没有订单。修正方式：MQ 消费失败自动重试（RocketMQ 默认 16 次，间隔递增），重试耗尽后进入死信队列由人工或补偿任务处理。

**DB 扣减失败**：MQ 消息消费成功，但 DB 的 CAS 更新返回影响行数 0（说明 DB 中的可用库存不足）。这种情况通常发生在 Redis 库存值与 DB 不一致时。修正方式：消费者检测到 DB 扣减失败后，将"已售数量"回补到 Redis（通过 Lua 脚本原子 INCRBY），并记录异常日志，由对账任务统一处理。

**运营后台修改库存**：运营在活动期间调整了数据库中的库存总量（如追加库存），但 Redis 中的可用库存没有同步更新。修正方式：运营后台的库存变更操作必须同步触发 Redis 更新（不是删除再重建，而是计算差值后做原子 INCRBY/DECRBY），并加分布式锁防止与秒杀扣减并发冲突。

#### 6.4 库存同步服务：不对等数据模型的桥梁

库存一致性问题比普通缓存更复杂，因为 Redis 和数据库中存储的语义可能不同。数据库中存储的是"总库存"和"已售数量"（或"可用库存"），而 Redis 中通常只存储"可用库存"用于快速判断。

推荐的做法是维护一个独立的"库存同步服务"，它的职责是：从数据库计算可用库存（总库存 - 已售未发货数量 - 预占数量），然后将结果写入 Redis。对于秒杀场景，这个服务只在活动开始前（预热）和活动结束后（清理）执行全量同步，活动期间只做增量修正：

```java
// 秒杀活动预热：活动开始前执行一次
public void preheatSecKillStock(String productId, int totalStock) {
    String key = "stock:" + productId;
    // 直接设置，不做 incr/decr
    redisTemplate.opsForValue().set(key, String.valueOf(totalStock));
    // 设置一个足够长的 TTL（大于活动持续时间 + 订单超时时间）
    redisTemplate.expire(key, 2, TimeUnit.HOURS);
}

// 活动期间增量修正：由对账任务定期触发
public void reconcileStock(String productId) {
    // 从数据库计算真实可用库存
    StockInfo info = stockMapper.getStockInfo(productId);
    int dbAvailable = info.getTotalStock() - info.getSoldCount() - info.getReservedCount();

    // 从 Redis 获取当前可用库存
    String redisStockStr = redisTemplate.opsForValue().get("stock:" + productId);
    int redisAvailable = (redisStockStr != null) ? Integer.parseInt(redisStockStr) : 0;

    int diff = dbAvailable - redisAvailable;
    if (diff != 0) {
        // 用 Lua 脚本原子修正差值（避免与并发扣减冲突）
        String luaScript =
            "local cur = tonumber(redis.call('GET', KEYS[1])) " +
            "if cur == nil then return -1 end " +
            "local newVal = cur + tonumber(ARGV[1]) " +
            "if newVal < 0 then newVal = 0 end " +
            "redis.call('SET', KEYS[1], newVal) " +
            "return newVal";
        redisTemplate.execute(
            new DefaultRedisScript<>(luaScript, Long.class),
            Collections.singletonList("stock:" + productId),
            String.valueOf(diff)
        );
    }
}
```

注意修正操作使用的是 Lua 脚本做原子加减，而不是直接 SET 覆盖——因为在校正脚本执行的瞬间，可能有扣减请求正在并发执行，直接覆盖会把刚刚扣减的量抹掉。

#### 6.5 多层一致性保障体系

秒杀场景的一致性保障需要多层纵深防御，但每一层的策略与普通场景不同：

第一层是业务层的 Write-Through（Redis 扣减 → MQ → DB 落库），处理正常流程中的绝大部分扣减请求。这是主路径，保证高并发下的性能和防超卖。

第二层是 MQ 消费补偿。消费失败自动重试，重试耗尽进入死信队列由补偿任务处理。补偿任务检查订单是否存在、DB 库存是否已扣，做出相应修正（补订单、回补 Redis 等）。

第三层是定时对账修正。每隔几分钟（秒杀期间可以缩短到 1 分钟）运行一次对账任务，比对 Redis 中的已售数量（初始库存 - 当前库存）与数据库中的实际订单数量。如果 Redis 已售 > DB 订单数，说明存在少卖，将差值回补到 Redis。对账修正必须通过 Lua 脚本原子执行，避免与并发扣减冲突。

第四层是活动结束后全量校准。秒杀活动结束后（无新扣减请求），以数据库为唯一权威数据源，重置 Redis 库存值或直接清理 key。这一层只在低峰期执行，不影响活动期间的性能。

```
活动期间一致性保障层次：
┌─────────────────────────────────────────────────────────────┐
│  第1层: Write-Through 主路径 (Redis Lua → MQ → DB)          │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  第2层: MQ 消费重试 + 死信队列补偿                      │  │
│  │  ┌─────────────────────────────────────────────────┐  │  │
│  │  │  第3层: 定时对账 (1min间隔, Lua脚本原子修正)       │  │  │
│  │  │  ┌───────────────────────────────────────────┐  │  │  │
│  │  │  │  第4层: 活动结束后全量校准 (以DB为准重置)    │  │  │  │
│  │  │  └───────────────────────────────────────────┘  │  │  │
│  │  └─────────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

#### 6.6 普通电商 vs 秒杀场景：策略对比

| 维度 | 普通电商 | 秒杀/大促 |
|------|---------|----------|
| Redis 库存 key 角色 | 读缓存（数据副本） | 写缓冲（实时计数器） |
| 是否允许删缓存 | 允许（Cache-Aside） | 绝对不允许（缓存击穿） |
| 写入方向 | DB → 缓存（Cache-Aside） | Redis → MQ → DB（Write-Through） |
| 数据权威 | DB 为实时权威 | 活动期间 Redis 为实时权威，DB 为最终权威 |
| 一致性修正时机 | 读时回填 + 定时对账 | 活动期间只增量修正，结束后全量校准 |
| 修正方式 | 删缓存或 SET 覆盖 | Lua 脚本原子加减差值 |
| Canal + Binlog | 推荐（通用同步方案） | 仅用于非秒杀库存的日常同步 |

这个对比表揭示了一个关键认知：秒杀库存的一致性问题不能用通用的缓存一致性方案来解决。它的核心矛盾是"极高的写并发"与"数据库有限的写能力"之间的冲突，解法是将 Redis 作为写操作的第一站，让数据库在异步通道中慢慢追认，而不是反过来。

### 七、库存回补与扣减的并发处理

库存回补（订单超时、退款、风控拦截等场景下将已扣减的库存还回去）与库存扣减（新订单占用库存）在时间上可能重叠。如果处理不当，回补操作可能被并发扣减"吞掉"，或者回补和扣减交叉执行导致数据不一致。

#### 7.1 回补与扣减的核心冲突

典型的冲突场景如下：一笔订单超时触发回补，系统准备将 Redis 中的库存 +N；与此同时，新的下单请求正在执行 Redis Lua 扣减。如果回补和扣减不是原子操作，可能出现：回补读到库存值 100，扣减也读到 100，扣减执行 DECRBY 使库存变为 95，回补执行 INCRBY 使库存变为 105——回补的 +N 被扣减覆盖了，或者反过来导致库存虚高。

在数据库层面同样存在冲突：如果回补和扣减都在同一个时间段内执行 `UPDATE stock SET stock = stock + N` 和 `UPDATE stock SET stock = stock - M`，虽然 MySQL 行级锁会串行化这些操作，但应用层如果采用"先读后写"模式（先 SELECT 当前库存，再计算新值后 UPDATE），就会产生经典的 lost update 问题。

#### 7.2 Redis 层：Lua 脚本保证原子性

解决方案的核心思路与扣减一致——使用 Lua 脚本将回补操作原子化：

```lua
-- 库存回补 Lua 脚本
-- KEYS[1]: 库存key, ARGV[1]: 回补数量
local key = KEYS[1]
local quantity = tonumber(ARGV[1])

-- 检查库存key是否存在
local stock = redis.call('GET', key)
if stock == false then
    -- key不存在，直接设置
    redis.call('SET', key, quantity)
    return quantity
end

-- 执行回补
local newStock = redis.call('INCRBY', key, quantity)
return newStock  -- 返回回补后的库存
```

由于 Redis 执行 Lua 脚本时是单线程原子操作，回补的 INCRBY 和扣减的 DECRBY 不可能同时执行——它们会被 Redis 的事件循环串行化处理。这意味着只要回补和扣减都通过 Lua 脚本执行，Redis 层面就不会出现并发冲突。

但需要注意一个问题：如果使用了库存分片（一个商品的库存分布在多个 Redis key 上），回补必须回到原来扣减的那个分片上，否则会导致分片间库存不均。解决方案是在扣减时记录"订单 → 分片编号"的映射关系：

```java
// 扣减时记录映射
redisTemplate.opsForValue().set(
    "deduct_segment:" + orderId,
    String.valueOf(segmentIndex),
    24, TimeUnit.HOURS  // TTL 应大于订单最大有效期
);

// 回补时查找原始分片
String segmentKey = redisTemplate.opsForValue().get("deduct_segment:" + orderId);
if (segmentKey != null) {
    int idx = Integer.parseInt(segmentKey);
    String key = "stock:" + productId + ":" + idx;
    redisTemplate.execute(rollbackScript, Collections.singletonList(key), quantity);
}
```

#### 7.3 数据库层：CAS + 幂等流水

数据库层面的回补操作必须满足两个要求：并发安全和幂等性。

**并发安全**通过 CAS 条件更新实现。与扣减时的 `WHERE stock >= quantity` 对称，回补时使用 `WHERE stock + quantity <= total_stock`（如果存在库存上限），防止回补导致库存超过实际总量：

```sql
-- 数据库回补（CAS 方式）
UPDATE product_inventory
SET stock = stock + #{quantity},
    updated_at = NOW()
WHERE product_id = #{productId}
  AND stock + #{quantity} <= total_stock;  -- 防止回补超限
```

**幂等性**通过库存流水表实现。每一笔扣减和回补都记录流水，以订单号 + 操作类型作为唯一键，重复操作会被唯一约束拒绝：

```sql
-- 流水表建表（唯一约束保证幂等）
CREATE TABLE inventory_log (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    order_id VARCHAR(64) NOT NULL,
    product_id VARCHAR(64) NOT NULL,
    change_type ENUM('DEDUCT', 'ROLLBACK') NOT NULL,
    quantity INT NOT NULL,
    segment_index INT DEFAULT -1,  -- 分片编号，-1 表示未分片
    created_at DATETIME NOT NULL,
    UNIQUE KEY uk_order_type (order_id, change_type)  -- 同一订单同类型操作只能一次
);

-- 回补时的完整流程（在同一事务中）
BEGIN;
-- 1. 插入回补流水（如果已回补过，唯一约束会报错，事务回滚）
INSERT INTO inventory_log (order_id, product_id, change_type, quantity, created_at)
VALUES (#{orderId}, #{productId}, 'ROLLBACK', #{quantity}, NOW());

-- 2. 执行回补
UPDATE product_inventory
SET stock = stock + #{quantity}
WHERE product_id = #{productId}
  AND stock + #{quantity} <= total_stock;

COMMIT;
```

唯一约束 `uk_order_type (order_id, change_type)` 确保同一笔订单的回补操作无论执行多少次，只有第一次能成功。后续重试会因为唯一键冲突而事务回滚，不会产生重复回补。

#### 7.4 回补与扣减的执行顺序

在系统层面，回补和扣减的调度需要遵循以下原则：

**先 DB 后 Redis**：回补操作应先执行数据库层面的回补（事务中包含流水写入和库存更新），成功后再执行 Redis 回补。这样即使 Redis 回补失败，数据库数据仍然是正确的，后续由补偿任务修正 Redis。反之，如果先回补 Redis 再回补 DB，DB 回补失败时 Redis 中多出来的库存就可能导致超卖。

**回补失败降级**：如果 Redis 回补失败，不要无限重试，而是将失败事件记录下来，由定时对账任务统一修正。在修正之前，Redis 中的库存可能偏少（少卖），但不会偏多（超卖），这是可以接受的——少卖只是损失部分销售机会，超卖则会引发客诉和资损。

**合并扣减方案中的回补**：在直播抢购等深库存场景中，有一种更精细的方案——"合并扣减"。它的核心思想是 Redis 仅做计数拦截，DB 的实际扣减通过延迟合并（如每 1 秒批量提交一次）来减少写压力。在这种架构下，回补操作需要先失效对应的 Redis 分桶（阻断新的扣减请求），再扫描该分桶关联的所有扣减明细计算真实扣减量，最后合并提交 DB。这个"先失效再扫描"的顺序从根本上杜绝了回补扫描期间有新扣减插入导致的少扫描问题。

```java
// 合并提交模块（简化逻辑）
public void mergeCommit(String productId, int segmentIndex) {
    // 1. 先失效 Redis 分桶，阻断新流量
    String bucketKey = "stock:" + productId + ":" + segmentIndex;
    redisTemplate.delete(bucketKey);

    // 2. 扫描该分桶的所有扣减明细
    List<DeductRecord> records = deductMapper.selectBySegment(productId, segmentIndex);
    int totalDeduct = records.stream().mapToInt(DeductRecord::getQuantity).sum();

    // 3. 合并提交到 DB（CAS 兜底）
    stockMapper.batchDeduct(productId, totalDeduct);

    // 4. 重新初始化分桶（将剩余可用库存加载回 Redis）
    int remaining = stockMapper.getAvailableStock(productId);
    redisTemplate.opsForValue().set(bucketKey, String.valueOf(remaining));
}
```

这种方案的压测数据显示，合并扣减的 TPS 峰值可达 3.2 万，相比逐笔扣减的 1.4 万提升了 1 倍以上，且库存扣减成功率从 80% 提升至 100%。

### 八、系统架构与全链路防护

高并发库存系统的设计不仅仅是选择一个扣减方案，而是需要从客户端到数据层的全链路防护。

#### 8.1 分层拦截

一个成熟的秒杀系统应该在每一层尽可能过滤掉无效请求：

客户端层面，活动未开始时禁用按钮，按钮点击后置灰并设置倒计时（如 3 秒内不可重复点击），加入验证码或答题机制拦截脚本和机器人。接入层在网关（Nginx、API Gateway）使用令牌桶或滑动窗口算法限流，直接拒绝超出后端处理能力的请求。应用层对下游核心接口设置熔断和降级策略，当系统负载过高时关闭推荐、评论等非核心功能，只保留交易链路。

#### 8.2 多级缓存

对于热点商品的库存查询（读操作远多于写操作），可以采用"本地缓存 + Redis 分布式缓存"的两级缓存架构：

应用服务器维护一个极短 TTL（如 1~3 秒）的本地缓存，大部分读请求在本地即可返回，大幅减少对 Redis 的访问压力。当库存发生变更时，通过 MQ 广播消息通知所有应用节点刷新本地缓存。需要注意的是，在实际执行扣减时必须使用 Redis 中的实时数据做二次校验，本地缓存仅用于前置的快速判断和售罄标记。

#### 8.3 降级与容灾

任何缓存系统都有宕机的可能。当 Redis 不可用时，系统应自动降级到数据库 CAS 方案，虽然吞吐量下降但至少保证服务可用。同时需要做好数据对账：Redis 与数据库的库存数据定期对账（建议每日凌晨全量对账 + 实时增量对账），发现不一致时以数据库为准修复。

### 九、方案对比与场景选型

| 方案 | 吞吐量 | 一致性 | 实现复杂度 | 适用场景 |
|------|--------|--------|-----------|---------|
| 数据库悲观锁 | 低（<500 QPS） | 强一致 | 低 | 低频库存操作、后台管理 |
| 数据库乐观锁 | 中（<2000 QPS） | 强一致 | 低 | 并发冲突率低的普通电商 |
| 数据库 CAS | 中高（<3000 QPS） | 强一致 | 低 | 中等并发的通用场景 |
| Redis Lua 预扣减 | 高（万级 QPS） | 最终一致 | 中 | 秒杀、大促等高并发场景 |
| Redis 分布式锁 | 中（<5000 QPS） | 强一致 | 中 | 库存补充、运营修改等低频写 |
| 库存分片 | 极高（线性扩展） | 最终一致 | 高 | 超大规模热点商品秒杀 |

典型的秒杀系统架构组合是：Redis Lua 预扣减（抗流量） + 消息队列异步削峰（解耦） + 数据库 CAS 兜底（保一致） + 定时对账补偿（纠偏差）。

### 十、最佳实践总结

**Redis Lua 脚本是防超卖的核心武器**。它将"查-判-扣"三步操作原子化，无需加锁即可获得数万 QPS 的吞吐量，是秒杀场景下的首选方案。

**数据库 CAS 是最后一道防线**。无论上层缓存方案多么精巧，数据库层面必须用 `WHERE stock >= quantity` 条件做兜底校验，确保即使缓存数据不一致也不会真正超卖。

**库存扣减和回滚必须幂等**。通过库存流水表记录每一笔操作，用订单号做幂等键，确保重复的扣减或回补请求不会产生副作用。

**消息队列承担异步解耦和削峰填谷的角色**。预扣减成功后立即返回用户"排队中"，后续流程由消费者异步处理，既保护了数据库，又提升了用户体验。

**回滚机制需要多策略组合**。延迟队列处理订单超时、事务消息保证跨服务一致性、定时对账修复数据偏差，三者配合才能覆盖所有异常场景。

**全链路限流和降级是系统稳定性的保障**。从客户端按钮置灰到网关令牌桶限流，再到服务层熔断降级，每一层都在为系统的稳定性兜底。

**缓存与数据库的一致性需要区分场景**。普通电商可用 Cache-Aside + Canal + Binlog 多层防御；秒杀场景的 Redis 库存 key 绝不能删除（否则缓存击穿打崩数据库），应采用 Write-Through 模式（Redis → MQ → DB），活动期间只用 Lua 脚本原子修正差值，活动结束后才全量校准。

**回补操作必须与扣减保持同等级别的原子性保障**。Redis 层用 Lua 脚本，数据库层用 CAS + 幂等流水表唯一约束，执行顺序坚持"先 DB 后 Redis"，宁可少卖不超卖。
