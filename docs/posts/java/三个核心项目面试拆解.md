## 三个核心项目面试拆解

> 面向 Java 后端 / 技术 PM 岗位，按「背景 → 内容与职责 → 技术框架 → 技术难点 → 解决方案 → 优化改进 → 面试话术」七个维度梳理。建议用 STAR（情境-任务-行动-结果）逻辑讲述，突出「你做了什么决策」而非「团队做了什么」。

## 项目一：商家发品智能体全链路建设（2025.11 至今 · 商品域技术一号位）

### 一、项目背景（面试怎么开场）

高德本地生活「扫街榜」上线后，榜单排名依赖商家侧数据的「有效、高质量、高权威」。要让榜单持续可信，就必须有更多优质商家有效入驻，并把商品信息又快又准地发布上来。传统人工发品流程存在两个致命问题：本地生活商品带「门店属性」（同一商品在不同门店/城市的指数不同），维护维度成指数级膨胀，人工成本极高；同步链路复杂、平台有反扒机制，图片信息解析准确率低，导致同步与上品效率低下。

一句话背景：**用 AI Agent + 多模态 + RAG，把「商家入驻到商品上架」这条链路从人工重操作改造成智能化自动上品，支撑榜单的数据规模与质量。**

### 二、项目内容与我的职责

作为商品域技术一号位，负责智能化商品发布流程和「商家智能体（Agent）」的整体建设，覆盖商品发布与三方供给迭代、AI 开发流程与范式能力建设。核心交付三块能力：智能化商品迁移与发品、三方供给平台化接入、AI 端到端全栈开发范式。

关键结果（面试必背数字）：商家发品链路 60% 以上智能化、全智能发品占比 40%；商详图片识别准确率 98% 以上；发品时效从 6min 降到 2.9min；节省运营成本 10w+；三方供给链路从 8 套融合为 5 套，发品能力承载 2000 tps，新供给接入时效降低 50%；拿了季度之星大奖。

### 三、技术框架 / 技术栈

后端主体 Java（微服务），大模型能力层用大模型平台编排 Workflow；多模态模型做商详图片解析；RAG 构建各行业结构化商品知识库；MCP（Model Context Protocol）+ Skill 封装商品迁移/发布的可复用工具能力；商家小蜜智能体做意图识别与召回；Prompt 工程做识别准确率调优。AI Coding 侧用 Claude / OpenCode / Cursor / Qoder，配合 SDD/ATDD 范式建设项目知识库与开发规范。

### 四、技术难点

第一，商品维护维度成指数级膨胀（门店 × 商品 × 指数），人工耗时过长，难以快速发布与更新。第二，商品同步链路复杂、大平台有反扒机制，有效数据难获取，图片信息解析准确率低，直接拖累同步与上品效率。第三，商户入驻放量后，需要商家智能体帮商家「快速且准确」上品，快和准往往难以兼得。

### 五、解决方案（行动细节 —— 面试重点展开）

针对耗时过长：把发品拆成「分步点、分步骤」提效，基于大模型平台搭建「标题推荐 + 类目预测」Workflow，用门店属性和离线数据做推荐填充，并改造审核机制来提升发品效率。

针对识别准确率低：建设完善的商品搬移链路，通过多模态模型搭建商详图片解析流程，用 Prompt 调优把识别准确率做到 95% 以上；再基于 RAG 搭建不同行业的结构化知识库，用知识库生产完整的商品信息，实现「识别完成即可发布上线」的快速能力。

针对快准兼得：基于商家小蜜智能体的能力，开发商品迁移和发布的 MCP 与 Skill 能力，根据识别出的商家意图召回对应 SOP 或 Skill，自动完成商品的初始化发布和修改。

### 六、优化改进 / 后续规划（面试加分项）

准确率上限：当前 98% 主要靠 Prompt + RAG，后续可引入「识别置信度分层 + 人工兜底回流」，把低置信样本沉淀为微调数据，做垂直行业小模型微调，进一步压低人工介入率。工程侧：Workflow 目前偏流程编排，可补充「效果 A/B、Prompt 版本灰度、指标看板」形成闭环可观测；MCP/Skill 能力可做能力市场化沉淀，让新行业接入从「开发」变「配置」。成本侧：多模态调用成本高，可做「缓存 + 模型分级路由（简单场景走小模型）」降本。

### 七、面试话术要点

强调「一号位」的技术决策与业务闭环：为什么选 Workflow 而不是纯规则、为什么用 RAG 而不是全靠大模型（幻觉与行业结构化）、MCP/Skill 如何做到复用。数字要能自证：98% 准确率是怎么量化验收的、2.9min 时效是端到端还是单环节。

## 项目二：度假交易和供应链治理专项（2024.10-2025.10 · 技术 PM、开发负责人）

### 一、项目背景

响应集团「去平台化」和「应用治理」战略，度假交易履约业务复杂、链路冗长、历史债多。目标是重新设计并落地度假交易和供应链的链路架构优化，治理腐化的应用代码，解决「业务定制链路过多导致功能无法模块化复用」的问题，打造干净、整洁、高效、稳定的交易履约系统链路。

一句话背景：**这是一个典型的「架构治理 + 性能优化 + 稳定性保障」三合一的存量系统重构项目。**

### 二、项目内容与我的职责

技术 PM 兼开发负责人，负责整体架构优化方案设计与落地。核心结果：全链路请求响应速度提升 50% 以上；年度绩效 3.75（超预期）。

### 三、技术框架 / 技术栈

Java 微服务；并发优化用 ThreadLocal、线程池、消息（MQ）解耦；缓存化改造关键链路；架构层引入「交易直连防腐层」应用解耦交易与供应链；能力编排基于 TMF（Trade Management Framework，交易域领域框架）做「域 / 能力 / 扩展点」的模块化。稳定性侧自研了一套「细粒度切流 + 数据 diff 比对监控」工具。

### 四、技术难点

第一，交易玩法丰富、对接供应链多，链路长，平均 RT 1.7s；能力弱的供应商响应最高到 10s 甚至更高，用户体验极差，急需优化。第二，优化过程涉及大量重构与链路变更，如何保障功能稳定性和重构结果的准确性。第三，供应链作为核心链路，定制业务繁重、代码腐化严重、大部分定制逻辑无法复用，链路不清晰、线上问题多。

### 五、解决方案（行动细节）

针对链路长依赖多、响应时间长：采用「关键链路缓存化 + 多业务处理并行化 + 供应链交互异步化」，利用 ThreadLocal、线程池、消息等技术，降低单次请求链路的最长路径，缩短全链路响应时间（RT 从 1.7s 显著下降，整体提速 50%+）。

针对重构风险（稳定性 + 准确性）：设计多维度、细粒度的切流配置，实现平滑灰度切换；并做了一套针对交易履约业务链路的「数据对比监控 diff 工具」，新老链路同时跑、实时比对结果，及时发现问题，保证重构准确性。

针对供应链腐化、无法复用：设计建设「交易直连防腐层应用」，解耦交易和供应链，按业务规则提供策略与能力，配合合规则引擎实现功能片段复用能力，把不可复用的定制逻辑收敛为可编排的能力。

### 六、优化改进 / 后续规划

性能：缓存化要防「缓存一致性 / 击穿 / 雪崩」，后续可做多级缓存 + 热点探测；异步化后要补「最终一致性对账 + 补偿」机制。可复用性：防腐层 + 能力编排后，可推进「能力资产化」，沉淀标准能力目录，让新玩法接入走配置化。可观测：diff 工具可以升级为常态化「线上流量回放 + 影子链路」平台，不只用于本次重构。

### 七、面试话术要点

这是最能体现「架构 + PM 双重能力」的项目。讲清楚三条主线：性能（并行/异步/缓存的取舍）、稳定性（切流 + diff 是重构灰度的核心方法论）、可复用（防腐层 + TMF 能力编排解决腐化）。RT 1.7s→提速 50% 要能说清瓶颈定位方法（是不是靠链路埋点 / 火焰图找最长路径）。

## 项目三：度假交易逆向能力建设专项（2024.08-2024.12 · 技术 PM、开发负责人）

### 一、项目背景

为提升度假业务服务和用户使用体验，提出度假交易「逆向能力」（即退款/退单侧）专项，通过闪电退、特殊退、全额退、过期自动退、协商退等多个能力建设，打造度假业务使用时全额退 + 快速退的用户心智。

一句话背景：**围绕「退得快、退得对」，把度假交易的逆向（退款）链路从零散、硬编码改造成标准化、可扩展的能力体系。**

### 二、项目内容与我的职责

技术 PM 兼开发负责人，主导逆向多能力建设。这个项目与工作经历中「主导实现门票退能力」呼应——退款问题进线降低 80% 以上、节省客服人工 10 人以上、月均节省成本 10w+，评选为半年度技术 PM 之星。

### 三、技术框架 / 技术栈

Java；一致性与并发用分布式锁；单据流转用状态机做状态校验；非标准退款流程基于 TMF 框架设计申请流程，创建对应「活动 / 域 / 能力 / 扩展点」来扩展退款能力。

### 四、技术难点

第一，特殊退场景「先提交审批后创建」，系统响应慢或用户重复多次点击，会导致产生多个单据，影响后续流程推进和节点状态判断。第二，特殊退款链路属于「非标准流程」，流程推进会影响原有链路的执行，且原流程中没有支撑该能力，直接硬编码会影响主链路、问题排查困难、加快代码腐化。

### 五、解决方案（行动细节）

针对单据重复创建和状态异常：加入「幂等设计」，利用分布式锁，基于「订单-用户」维度做创建单据，采用状态机校验单据状态，保障单据流转的正确性和不可逆性（退款单据的状态只能单向流转，不能回退）。

针对非标准退款流程侵入主链路：基于 TMF 框架设计申请流程，创建对应的活动、域、能力和扩展点，把特殊退、协商退等非标能力「挂载」到扩展点上，不侵入主链路、丰富退款能力，同时避免代码腐化。

### 六、优化改进 / 后续规划

一致性：分布式锁要考虑锁超时 / 死锁 / 锁粒度，可补「兜底幂等表 + 异步对账」双保险。可扩展：TMF 扩展点体系可继续沉淀「退款能力标准模板」，新退款玩法走配置。体验：过期自动退、闪电退可结合规则引擎做「自动决策 + 秒退」，进一步减少进线。可观测：退款单据状态机可做全链路轨迹追踪，客服可自助排障，进一步压低人工。

### 七、面试话术要点

这是考察「分布式一致性 + 领域建模」的项目。两个技术点必答漂亮：一是幂等（分布式锁 + 订单-用户维度 + 状态机不可逆），能延展讲「为什么状态机比 if-else 好」；二是 TMF 扩展点如何隔离非标流程避免腐化，体现你对「可扩展架构」的理解。数字：进线降 80%、省 10 人力、月省 10w+。

## 通用面试建议（三个项目共性）

技术主线清晰：项目一是「AI Agent / RAG / Workflow / MCP」，项目二是「架构治理 / 性能 / 稳定性」，项目三是「分布式一致性 / 领域建模 / TMF」。面试时按岗位侧重挑主推项目——偏 AI 岗推项目一，偏后端架构岗推项目二/三。

准备「反问式追问」：面试官一定会追问数字怎么来的、方案的取舍（为什么不用别的方案）、遇到的最大坑。每个项目准备 1 个「踩坑 + 复盘」的故事最加分。

统一话术骨架：背景痛点（有数据）→ 我的角色与决策 → 技术方案（有取舍）→ 结果（有量化）→ 复盘与优化。突出「一号位 / 技术 PM」的 owner 视角：需求拆解、方案设计、上线保障闭环。

# 第二部分：面试官高频追问 + 参考答案

> 下面每个问题都给出「面试官为什么问」+「参考答话」。参考答话是骨架，需要你替换成自己的真实细节，切忌背诵。

## 项目一 · 商家发品智能体（AI 方向追问）

**Q1：识别准确率 98% 是怎么统计和验收的？**
面试官想确认这是不是「拍脑袋数字」。参考答话：我们建了一套评测集，从真实商家商详里抽样约 N 条覆盖各行业，人工标注「正确结构化结果」作为 ground truth，用识别结果和标注做字段级比对（标题、类目、规格、价格、图片属性等），准确率 = 正确字段数 / 总字段数。上线后再用「运营修改率」做线上反向验证——运营发布前修改越少，说明识别越准。Prompt 调优前约 85%，加入 RAG 行业知识库 + few-shot 后到 95%+，再叠加多模态图片解析校验做到 98%+。

**Q2：为什么要用 RAG，而不是直接让大模型输出商品信息？**
考察你对大模型幻觉与工程边界的理解。参考答话：纯大模型有三个问题——一是幻觉，会编造不存在的规格/参数；二是不同行业的结构化 schema 差异极大（餐饮、酒店、玩乐、丽人字段完全不同），靠 Prompt 硬塞维护成本高；三是无法保证输出符合我们平台的类目体系。RAG 的价值是把「行业结构化知识库 + 类目标准」作为检索上下文注入，让模型在「有据可依」的范围内生成，既降幻觉又保证字段规范，知识库更新也不用改模型。

**Q3：MCP 和 Skill 到底解决了什么，和普通 API 有什么区别？**
参考答话：普通 API 是给「人写的代码」调的，MCP 是给「大模型/Agent」调的标准协议——它把商品迁移、发布、修改这些操作封装成模型可理解、可自主编排的工具，模型根据识别出的商家意图自己决定调用哪个能力。Skill 则是把「一类标准操作流程（SOP）」沉淀成可复用单元。区别在于：传统模式是「代码写死流程调 API」，Agent 模式是「模型理解意图 → 召回 SOP/Skill → 自主编排 MCP 工具」，新场景接入从开发变成配置召回。

**Q4：Workflow 编排和传统 if-else 规则引擎相比，好在哪？出错了怎么排查？**
参考答话：发品是多步骤（标题推荐→类目预测→图片解析→信息补全→审核），Workflow 把每步做成可插拔节点，便于灰度、复用和监控每步耗时/成功率；纯 if-else 耦合高、难观测。排查上每个节点有独立日志和指标，某步准确率掉了能快速定位是 Prompt、模型还是知识库的问题。

**Q5：全智能发品占 40%，剩下 60% 为什么还不能全自动？**
考察边界意识。参考答话：剩下的是低置信 / 强合规 / 复杂规格场景，我们做了「置信度分层 + 人工兜底」，低于阈值的转人工，避免错误上品影响榜单权威性。这也是后续微调小模型、继续提升自动化率的方向。

## 项目二 · 交易供应链治理（架构性能追问）

**Q6：RT 1.7s 的瓶颈是怎么定位的？**
考察性能优化方法论。参考答话：先做全链路埋点（trace），统计各下游依赖的耗时占比和调用次数，画出调用拓扑找「最长路径」；发现瓶颈集中在串行调用多个供应商、部分弱能力供应商 RT 高达 10s，以及重复查询。定位后才对症下药：能并行的并行、能异步的异步、能缓存的缓存。

**Q7：并行化 + 异步化 + 缓存化，具体怎么落地？各自的坑是什么？**
参考答话：并行——把无依赖关系的多供应商查询用线程池并发（CompletableFuture），总耗时从「串行求和」变「取最大值」；坑是线程池要隔离（不同业务不同池，防止互相拖垮）、要设超时和降级。异步——非核心链路（如通知、日志、部分供应链回写）用 MQ 解耦；坑是最终一致性，要有对账补偿。缓存——热点、低频变更数据缓存；坑是一致性、击穿、雪崩，要做过期打散 + 空值缓存 + 热点探测。

**Q8：你提到用了 ThreadLocal，在这里的作用是什么？有什么风险？**
高频八股 + 项目结合。参考答话：并行化后，一次请求会跨多线程，用 ThreadLocal 传递请求上下文（用户、链路标、trace）。风险有两个：一是线程池复用线程，ThreadLocal 不清理会串数据/内存泄漏，必须用完 remove；二是父子线程不传递，跨线程要用 InheritableThreadLocal 或 TransmittableThreadLocal（阿里 TTL）来传递上下文。

**Q9：重构这么大，你怎么保证不出线上事故？diff 工具原理是什么？**
这是项目二最出彩的点。参考答话：核心方法是「灰度切流 + 双跑 diff」。切流——设计多维度细粒度切流配置（按业务/比例/白名单），先 1% 灰度逐步放量，出问题秒回滚。diff——新老链路同时执行，对两边的出参结果做字段级实时比对，不一致就告警并落库，让我们在放量前就发现逻辑偏差。这样重构既平滑又能自证准确性。

**Q10：什么是防腐层（ACL）？为什么能解决供应链腐化？**
DDD 概念结合项目。参考答话：防腐层是 DDD 里的 Anti-Corruption Layer，在交易域和供应链域之间加一层「翻译/隔离」，交易只依赖防腐层暴露的标准能力接口，不直接依赖各供应商的私有协议和定制逻辑。这样供应链的脏乱差被挡在防腐层之外，交易主链路保持干净；新增供应商只需在防腐层做适配，配合 TMF 能力编排实现片段复用，从根上抑制腐化蔓延。

## 项目三 · 逆向退款能力（一致性 / 领域建模追问）

**Q11：幂等具体怎么做的？为什么按「订单-用户」维度加分布式锁？**
参考答话：用户重复点击/系统慢会重复提交，导致一个退款诉求生成多张单。我们用分布式锁（如 Redis/tair 锁）以「订单 ID + 用户 ID」为 key 加锁，保证同一订单同一用户同一时刻只有一个创建请求进入；同时用唯一键 + 状态机做二次幂等兜底（即使锁失效，唯一约束也拦得住重复单）。选这个维度是因为退款的业务唯一性就落在「谁的哪个订单」上。

**Q12：状态机相比 if-else 判断状态好在哪？**
参考答话：退款单状态流转复杂（申请→审批→退款中→成功/失败/关闭），且要求不可逆。用状态机把「允许的状态迁移」显式建模成一张表，任何流转都先校验「当前态 → 目标态」是否合法，非法直接拒绝。好处：一是防止状态回退和乱跳（保证不可逆），二是新增状态/流转只改配置不改散落的 if-else，三是可视化、可审计。

**Q13：TMF 框架的域/能力/扩展点是什么？为什么非标退款要挂扩展点？**
参考答话：TMF 是交易域的扩展框架，核心是「业务身份 → 域 → 能力 → 扩展点」。主流程定义标准能力（如退款申请），不同业务的差异化逻辑（特殊退、协商退）做成扩展点的不同实现，运行时按业务身份路由到对应扩展点。好处是非标流程不侵入主链路——不用在主流程里写一堆 if(是特殊退)，避免代码腐化，新增退款玩法只加扩展点实现即可。

**Q14：退款进线降 80% 主要靠什么？**
参考答话：一是自动化退款能力（闪电退、过期自动退）让用户自助秒退，不用找客服；二是状态和单据准确性提升，减少了「退款卡单/状态不对」这类咨询；三是流程标准化后异常变少。进线降 → 客服人力省 10 人 → 月省 10w+ 是一条因果链。

# 第三部分：核心技术知识点深挖附录

> 面试官会脱离项目单独考这些概念，务必能独立讲清楚。

## AI 工程侧

**RAG（检索增强生成）**：检索（把知识切块 chunk → 向量化 embedding → 存向量库）+ 增强（query 向量检索 Top-K 相关块）+ 生成（把检索结果拼进 Prompt 让模型作答）。解决幻觉、知识时效、私域知识三大问题。关键调优点：切块粒度、embedding 模型、检索召回率、重排（rerank）、上下文长度。

**Prompt 工程**：角色设定 + 任务描述 + 约束 + few-shot 示例 + 输出格式（JSON schema）。稳定性技巧：结构化输出、思维链（CoT）、示例覆盖边界 case、温度调低。你的项目里「识别准确率 85%→95%」主要就是靠 few-shot + 输出 schema 约束 + RAG 上下文。

**Agent**：具备「感知(理解意图)→规划(编排步骤)→行动(调工具)→反思」能力的大模型应用。你的商家智能体 = 意图识别 + SOP/Skill 召回 + MCP 工具调用。

**多模态**：图文联合理解，商详图片解析就是视觉模型提取图中文字/属性/规格，再结构化。

## Java 并发与性能

**线程池核心参数**：corePoolSize、maxPoolSize、队列、拒绝策略、keepAlive。项目里要点：不同业务用独立线程池做隔离，防止一个慢供应商拖垮全部；配超时 + 降级。

**CompletableFuture**：并行编排利器，allOf/thenCombine 聚合多个异步结果，把串行改并行。

**ThreadLocal**：线程内变量副本，底层是 ThreadLocalMap（key 弱引用防泄漏，但 value 不会自动清，必须 remove）。跨线程传递用 TTL（TransmittableThreadLocal）。

**分布式锁**：Redis(setnx+过期+唯一value+lua释放) 或 Redisson(看门狗续期)。要点：可重入、锁超时、防误删、避免死锁；本身不能替代业务幂等，要配唯一键兜底。

## 架构与稳定性

**幂等**：同一请求执行多次结果一致。方案：唯一键约束、状态机、token、分布式锁、去重表。

**状态机**：显式定义状态 + 合法迁移，校验后流转，保证不可逆与可审计。

**防腐层 ACL / DDD**：域隔离与翻译层，保护核心域不被外部脏模型污染。

**缓存三问题**：穿透（空值缓存/布隆过滤器）、击穿（热点 key 加锁/永不过期逻辑过期）、雪崩（过期时间打散 + 多级缓存 + 限流降级）。

**灰度发布方法论**：细粒度切流（比例/白名单/业务维度）+ 双跑 diff 比对 + 可秒级回滚，是存量系统重构的黄金组合。

**最终一致性**：异步/MQ 场景下用「本地消息表 / 事务消息 / 定时对账补偿」保证数据最终一致。

## MQ（消息队列）

作用：解耦、异步、削峰。要会答的坑：消息丢失（生产确认+持久化+消费 ack）、重复消费（消费端幂等）、顺序（同 key 同分区）、堆积（扩消费者/限流）。
