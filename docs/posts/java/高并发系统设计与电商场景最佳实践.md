## 高并发系统设计与电商场景最佳实践

### 什么是高并发

高并发（High Concurrency）是指在某一时刻或极短的时间窗口内，系统同时接收到大量请求并需要快速、正确地处理这些请求的能力。在电商场景中，高并发通常出现在大促活动（如双 11、618）、限时秒杀、热门商品开售等场景，瞬时流量可能是日常峰值的数十倍甚至上百倍。

高并发系统设计的核心目标不是单纯追求"能处理多少请求"，而是在极端流量压力下保持系统的可控稳定性——核心交易链路可用、数据一致、响应时间在可接受范围内。

### 核心性能指标

设计和评估高并发系统之前，必须理解几个关键性能指标及其相互关系。

**QPS（Queries Per Second）** 衡量系统每秒能处理的请求数量，是评估系统吞吐能力的最直观指标。一个 QPS 为 1000 的服务意味着每秒能处理 1000 个请求。

**TPS（Transactions Per Second）** 衡量系统每秒能完成的完整事务数量。一次事务可能包含多个请求（如一次下单涉及创建订单、扣减库存、扣款三个操作），因此 TPS 通常低于 QPS，更能反映系统的实际业务处理能力。

**RT（Response Time）** 即响应时间，指从客户端发出请求到收到服务器完整响应所经历的总时长，包含网络传输、服务器排队、业务处理等所有环节的耗时。在高并发场景下，RT 通常会随着并发量增加而上升。

**吞吐量（Throughput）** 指系统在单位时间内成功传输或处理的数据量，综合反映了系统的带宽、处理能力和并发容量。

**并发数（Concurrency）** 指系统在同一时刻正在处理的请求数量。并发数不等于 QPS——一个请求的 RT 越长，同一时刻"在途"的请求就越多，并发数就越高。它们之间的关系可以用 Little's Law 表达：`并发数 = QPS × 平均RT`。

这些指标深度互联：QPS/TPS 的提升往往伴随着 RT 的变化；当请求排队严重时，吞吐量会下降，RT 会急剧上升。评估系统性能时需要多维度综合分析，而非只看单一指标。

### 高并发的底层原理

#### I/O 模型与多路复用

高并发网络服务器的核心挑战是如何用有限的线程高效地管理海量的网络连接。这涉及到 I/O 模型的演进。

**阻塞 I/O（BIO）** 是最简单的模型——每个连接需要一个独立线程处理，线程在等待数据时会阻塞。当并发连接数达到数千时，线程的创建、销毁和上下文切换开销会成为系统瓶颈。

**I/O 多路复用** 允许单个线程同时监控大量文件描述符（网络套接字），当某个描述符就绪时才进行处理。主流实现有三种：

select 使用位图数组跟踪文件描述符，时间复杂度为 O(N)，且有 1024 个描述符的硬性上限。

poll 用链表替代位图，去除了数量限制，但仍有 O(N) 的遍历开销和每次调用时用户态/内核态之间的完整数据拷贝。

epoll（Linux 专属）使用红黑树管理描述符、双向链表存储就绪事件，只将就绪的描述符拷贝到用户空间，事件检测复杂度降为 O(1)。它特别适用于连接数巨大但大多数连接空闲的场景（如 Web 服务器）。epoll 支持水平触发（Level-Triggered，持续通知直到数据被读完）和边缘触发（Edge-Triggered，仅通知一次，应用必须循环读取直到 EAGAIN）两种模式。

**Reactor 模式** 是基于 I/O 多路复用的高并发网络架构标准模式。它将事件的多路复用（由 Selector 完成）和事件的处理（由 Handler 完成）解耦，使得系统可以灵活扩展。典型的 Reactor 架构包含一个 Acceptor（接受新连接）和多个 Reactor 线程（处理已建立连接的读写事件），Netty、Nginx、Redis 等高性能服务器都采用了这一模式。

#### 并发模型

除了 I/O 层面的优化，应用层的并发模型也决定了系统的并发上限。

**多线程模型** 通过创建多个线程并行处理请求。线程是操作系统调度的基本单位，但创建和上下文切换的开销较高。线程池通过预创建和复用线程来规避这一开销。

**协程模型**（如 Go 的 goroutine、Kotlin 的 coroutine）是用户态的轻量级线程，创建和切换的开销极低（通常为纳秒级），一个线程可以运行数万个协程。Go 的 goroutine 配合 channel 通信，是高并发服务的天然选择。

**事件驱动/异步模型**（如 Node.js 的事件循环、Java 的 CompletableFuture）通过回调或 Future/Promise 机制实现非阻塞 I/O，单个线程就能处理大量并发连接，适合 I/O 密集型场景。

### 高并发系统的核心策略

#### 一、缓存——让数据离计算更近

缓存是高并发系统中最核心的性能优化手段，本质是将热点数据放在离计算更近的地方，减少对慢速后端（数据库、远程服务）的访问。

**多级缓存架构** 是电商系统的标准配置。第一级是浏览器缓存和 CDN 边缘节点，缓存静态资源（图片、CSS、JS）；第二级是应用本地缓存（如 Caffeine、Guava Cache），速度最快（纳秒级），但容量有限且多实例间不一致；第三级是分布式缓存集群（如 Redis），容量大、多实例共享，但有一次网络 RTT 开销（通常 1-5ms）。

在电商商品详情页场景中，一个典型的多级缓存设计是：CDN 缓存商品图片（命中率 > 95%）→ 本地缓存极热点商品基本信息（TTL 30 秒，命中率约 30%）→ Redis 缓存商品详情、价格、库存（命中率约 70%）→ 数据库兜底。整体缓存命中率每提升 10%，数据库的压力可能下降 30% 以上。

**缓存三大经典问题及其解决方案**：

缓存穿透（查询不存在的数据，每次都穿透到数据库）——使用布隆过滤器（Bloom Filter）在缓存层前拦截，布隆过滤器用多个哈希函数将元素映射到位数组，可能误判（不存在的被判为存在）但不会漏判（存在的不会被拦截）；对于穿透到数据库的请求，缓存空值并设置短 TTL（如 5 分钟）。

缓存击穿（热点 Key 过期瞬间大量请求涌入数据库）——使用互斥锁（如 Redis SETNX）只允许一个线程回源查数据库并重建缓存，其他线程等待或返回旧值；对于极热点 Key，可以设置永不过期，由后台线程异步更新。

缓存雪崩（大量 Key 同时过期，数据库被打垮）——给过期时间加随机值（如基础 TTL + 1~5 分钟的随机偏移），避免集中过期；多级缓存降级（Redis 不可用时本地缓存兜底）；限流保护数据库。

#### 二、异步——让非关键路径不阻塞主流程

异步化是提升系统吞吐量的核心手段，它将不需要实时返回结果的操作从主流程中剥离，通过消息队列或后台任务异步执行。

在电商下单场景中，同步路径只需要完成"创建订单 + 扣减库存"两个核心操作，而发送通知短信、积分增加、优惠券核销、物流预报、风控审核等操作全部异步化。这样每个同步请求的处理时间从数百毫秒压缩到几十毫秒，系统 QPS 可以提升一个数量级。

消息队列同时充当流量缓冲区——秒杀产生的海量订单请求先进入队列，订单服务按照自身最大处理能力平稳消费，避免被瞬时流量击穿。这就是"削峰填谷"的本质。

#### 三、池化——减少资源创建销毁的开销

池化技术的核心思想是"空间换时间"——预先创建并复用资源，避免频繁创建和销毁带来的性能损耗。

**数据库连接池**（如 HikariCP、Druid）预先建立一批数据库连接并复用。一次数据库连接的建立（TCP 握手 + 认证）可能需要 4ms，而一次 SQL 执行只需要 1ms，如果不使用连接池，连接建立的开销会数倍于实际业务处理。连接池的关键配置包括最小连接数（建议 10 左右）、最大连接数（建议 20-30 左右，过多反而因上下文切换降低性能）、空闲连接检测线程（定期探活，防止数据库端静默断开）。

**线程池** 预先创建一组工作线程来处理任务。JDK ThreadPoolExecutor 的工作流程是：任务到达 → 创建核心线程（corePoolSize）处理 → 核心线程满则入队列等待 → 队列满则创建非核心线程（直到 maxPoolSize）→ 全满则执行拒绝策略。对于 I/O 密集型的 Web 应用，应该优先创建线程（而非先堆积队列），线程数可以设置为 CPU 核数的 2-4 倍。严格避免使用无界队列（如 LinkedBlockingQueue 不指定容量），防止内存耗尽。启动时调用 `prestartAllCoreThreads()` 预热线程池，避免系统刚启动时响应缓慢。

**对象池** 预先创建一批对象实例，使用时从池中获取，用完归还而非销毁。对于创建成本高的对象（如数据库连接、SSL 上下文、大型缓冲器），对象池可以显著减少 GC 压力和创建延迟。

#### 四、限流——控制进入系统的流量速率

限流是保护系统不被瞬时流量压垮的第一道防线，本质是"在入口控制流量速率，超过阈值则拒绝或排队"。

**常见限流算法**：

固定窗口计数器在固定时间窗口（如 1 秒）内计数，超过阈值则拒绝。实现简单但存在"临界点突刺"问题——窗口切换瞬间可能出现 2 倍阈值的流量。

滑动窗口将时间窗口细分为多个小格子，只统计最近一段时间内的请求数，平滑了固定窗口的临界点问题，但实现更复杂。

漏桶算法（Leaky Bucket）以恒定速率处理请求，超出的请求排队或丢弃。它能平滑流量但无法应对突发。

令牌桶算法（Token Bucket）以恒定速率生成令牌，请求需要获取令牌才能被处理。它允许一定程度的突发流量（桶中积累的令牌可以被瞬时消耗完），是实践中最常用的算法。

**限流的层级**：网关层限流（保护整个后端，基于 IP/用户 ID/API Key）、应用层限流（保护单个服务，基于接口 QPS）、资源层限流（保护数据库/缓存，基于连接数/线程数）。Sentinel 是阿里巴巴开源的流量控制组件，支持单机限流、集群限流、热点参数限流（针对特定爆款商品 ID 单独限流），经过多年双 11 大促验证。

#### 五、熔断与降级——故障隔离与有损服务

**熔断（Circuit Breaker）** 防止下游服务故障引发雪崩效应。当下游服务的错误率或响应时间超过阈值时，熔断器打开，后续请求直接快速失败而不再调用下游。经过冷却期后进入半开状态，放行少量探测请求，如果成功则关闭熔断器恢复正常。在电商系统中，商品详情页的评论服务挂了不应该影响商品浏览和下单——这就是熔断的价值。

**降级（Degradation）** 是在系统压力过大时主动舍弃非核心功能以保障核心链路的策略。大促期间典型的降级操作包括：关闭推荐系统（返回默认列表）、关闭实时评价功能、将异步通知从实时推送改为延迟发送、将图片搜索降级为文本搜索。降级的核心原则是"有损服务"——牺牲部分用户体验换取核心交易链路的可用性。

熔断和降级的区别在于：熔断是被动的（由下游故障触发），降级是主动的（由系统压力触发或人工开关控制）。两者通常配合使用。

#### 六、水平扩展——用更多的机器扛更多的流量

当单机优化做到极致仍然无法承载流量时，水平扩展（加机器）是最终手段。

**无状态设计** 是水平扩展的前提——应用层不保存任何会话状态（Session 放入 Redis，文件放入对象存储），任何一个实例都可以处理任何请求。

**负载均衡** 将流量分发到多个实例。常见的算法包括轮询（Round Robin）、最少连接数（Least Connections）、IP 哈希（同一 IP 始终路由到同一实例）。Nginx、HAProxy、云厂商的 SLB/ALB 是常用的负载均衡器。

**弹性扩缩容** 利用 Kubernetes 的 HPA（Horizontal Pod Autoscaler）根据 CPU 使用率、QPS 或自定义指标自动增减实例数量。大促前预先扩容（预热），大促后自动缩容以节省成本。

#### 七、数据库优化——数据层的最后防线

数据库通常是高并发系统中最难扩展的环节，需要从多个层面优化。

**读写分离** 将读请求分摊到从库，主库只处理写请求。需要注意的是主从同步存在延迟（通常毫秒级到秒级），关键业务路径（如支付后查询订单状态）可能需要强制路由到主库。

**索引优化** 确保所有高频查询都走索引，避免全表扫描。联合索引的字段顺序需要匹配查询条件（最左前缀原则）。

**分库分表** 当单表数据量超过千万级或单库写入成为瓶颈时考虑。垂直分库按业务域隔离，水平分表按分片键（通常是用户 ID）打散数据。分库分表引入分布式事务、跨库 JOIN、全局唯一 ID 等新问题，因此它是数据库优化的最后手段，而非第一步。

**SQL 优化** 将复杂查询拆分为多个简单查询在应用层组装、避免 `SELECT *` 只查询需要的字段、批量操作代替逐条操作、使用 `EXPLAIN` 分析查询计划。

### 电商大促场景的全链路方案

电商大促（如双 11）是高并发系统设计的终极考场，需要从前到后、从入口到数据层的全链路协同。

**流量入口层**：CDN 缓存所有静态资源（商品图片、CSS、JS），承担 70% 以上的流量；DNS 智能解析将用户路由到最近的接入点；API Gateway 执行限流、鉴权、恶意请求拦截。

**前端层**：静态资源走 CDN、动态请求合并减少 HTTP 请求数量、按钮防重复点击、答题/验证码分散请求峰值（将瞬时的秒杀流量平摊到 5-10 秒的答题过程中）。

**应用层**：微服务按业务域独立部署（秒杀服务与主站隔离，防止秒杀流量冲垮主站）、无状态设计 + 弹性扩缩容、热点数据预加载（大促开始前将爆款商品数据预热到缓存中）。

**缓存层**：多级缓存体系（本地缓存 + Redis 集群）、热点 Key 永不过期 + 后台异步更新、缓存穿透/击穿/雪崩的三层防御。

**消息层**：RocketMQ 异步解耦非核心操作、削峰填谷缓冲瞬时订单流量、事务消息保证最终一致性。

**数据层**：读写分离 + 分库分表、Redis 原子扣减（Lua 脚本）+ 数据库乐观锁兜底防超卖、Elasticsearch 承接复杂的商品搜索和商家维度查询。

**服务治理层**：限流控制总入口流量、熔断隔离非核心服务故障、降级关闭非核心功能、全链路压测提前验证容量（使用影子库/影子表隔离压测数据）。

**可观测性层**：日志聚合（ELK/Loki）+ 指标监控（Prometheus + Grafana，秒级粒度展示核心链路 QPS、RT、错误率）+ 链路追踪（SkyWalking/Jaeger，全局 Trace ID 快速定位慢节点）+ 智能告警 + 自动触发预案。

### 常见误区与注意事项

**误区一：高并发 = 无限加机器**。水平扩展有上限——数据库连接数、分布式锁竞争、网络带宽都可能成为瓶颈。加机器之前必须先找到并优化系统的真正瓶颈点。

**误区二：缓存能解决一切问题**。缓存本身也是分布式系统，也会出故障（缓存穿透/击穿/雪崩、缓存与数据库不一致、Redis 主从切换丢数据）。引入缓存解决了读性能问题但带来了新的复杂性问题。

**误区三：忽视预热**。系统刚启动时连接池为空、缓存为空、JIT 未编译，第一批请求的 RT 会远高于稳态。大促前必须进行缓存预热、连接池预热、JVM 预热（通过小流量逐步放大）。

**误区四：分布式锁设置超时过长或无超时**。如果持有锁的节点崩溃且锁无超时，会导致死锁——其他节点永远无法获取锁，相关功能永久不可用。

**误区五：全链路压测不做数据隔离**。在生产环境压测时如果不使用影子库/影子表隔离压测数据，压测产生的脏数据会污染真实业务数据。

### 面试高频问题与回答思路

高并发是后端和架构面试中最核心的考察领域之一。以下梳理 15 道高频面试题及推荐的回答思路。

#### Q1：什么是 QPS、TPS、RT、并发数？它们之间的关系是什么？

**回答思路**：QPS 是每秒处理的请求数，TPS 是每秒完成的完整事务数（一次事务可能包含多个请求，因此 TPS ≤ QPS），RT 是从发送请求到收到响应的总耗时，并发数是同一时刻正在处理的请求数。它们的关系可以用 Little's Law 表达：`并发数 = QPS × 平均 RT`。比如一个系统 QPS 为 1000，平均 RT 为 50ms，那么并发数就是 50。面试中能说出 Little's Law 是加分项。

#### Q2：I/O 多路复用（select/poll/epoll）的区别是什么？为什么 epoll 性能更好？

**回答思路**：三者都是让单个线程监控多个文件描述符的机制。select 用位图数组，有 1024 上限，时间复杂度 O(N)；poll 用链表，无数量限制，但仍是 O(N) 遍历且每次需要完整拷贝描述符集合；epoll 用红黑树管理描述符 + 双向链表存储就绪事件，只将就绪的描述符拷贝到用户空间，事件检测复杂度 O(1)。epoll 的优势在连接数巨大但大多数空闲时特别明显（如 Web 服务器），这也是 Nginx、Redis、Netty 都使用 epoll 的原因。面试官可能追问"水平触发和边缘触发的区别"——水平触发（LT）在数据未读完时会持续通知，边缘触发（ET）只通知一次，应用必须循环读取直到 EAGAIN。

#### Q3：什么是 Reactor 模式？它为什么能支撑高并发？

**回答思路**：Reactor 模式将事件的多路复用（由 Selector 完成）和事件的处理（由 Handler 完成）解耦。典型的 Reactor 架构包含一个 Acceptor（接受新连接）和多个 Reactor 线程（处理已建立连接的读写事件）。它能支撑高并发的原因是：一个线程通过 I/O 多路复用管理数千个连接，避免了"每连接一线程"模型中线程创建和上下文切换的巨大开销。Redis 使用单线程 Reactor（因为它的瓶颈在网络和内存而非 CPU），Netty 使用主从 Reactor 多线程模型（Boss Reactor 接受连接，Worker Reactor 处理读写）。

#### Q4：线程池的核心参数有哪些？如何合理配置？

**回答思路**：JDK ThreadPoolExecutor 的七个核心参数：corePoolSize（核心线程数）、maxPoolSize（最大线程数）、keepAliveTime（非核心线程空闲存活时间）、unit（时间单位）、workQueue（任务队列）、threadFactory（线程工厂）、handler（拒绝策略）。

配置原则：CPU 密集型任务（如加密计算）线程数设为 CPU 核数 + 1；I/O 密集型任务（如 Web 请求、数据库查询）线程数设为 CPU 核数的 2-4 倍（因为线程大部分时间在等待 I/O）。严格避免无界队列（防止 OOM），队列大小应根据业务 RT 和 QPS 计算。启动时调用 `prestartAllCoreThreads()` 预热。面试官可能追问"任务提交流程"——先创建核心线程 → 入队列 → 创建非核心线程 → 执行拒绝策略。

#### Q5：数据库连接池为什么能提升性能？如何配置？

**回答思路**：一次数据库连接建立（TCP 三次握手 + 认证）可能需要 4ms，而一次 SQL 执行只需 1ms。如果不使用连接池，连接建立的开销是 SQL 执行的 4 倍。连接池预先建立并复用连接，将这部分开销降到接近零。

关键配置：最小连接数（建议 10 左右，保证空闲时也有足够的连接可用）、最大连接数（建议 20-30 左右，过多反而因为数据库端的上下文切换降低性能）、空闲连接探活（后台线程定期检测，防止数据库端静默断开导致拿到死连接）。面试官可能追问"拿到连接后是否需要验证有效性"——生产环境建议关闭 checkout 时的验证（每次验证增加一次 RTT），改为后台探活。

#### Q6：缓存穿透、缓存击穿、缓存雪崩分别是什么？如何解决？

**回答思路**：这三个问题是必考题，需要清晰区分。

缓存穿透（查询不存在的数据，每次都穿透到数据库）——解决方案：布隆过滤器（Bloom Filter）拦截 + 缓存空值（短 TTL）。布隆过滤器可能误判（不存在的被判为存在），但不会漏判（存在的不会被拦截）。

缓存击穿（热点 Key 过期瞬间大量请求涌入）——解决方案：互斥锁（SETNX）只允许一个线程回源 + 热点 Key 永不过期（后台异步更新）。

缓存雪崩（大量 Key 同时过期）——解决方案：过期时间加随机值（避免集中过期）+ 多级缓存降级 + 限流保护数据库。

面试官通常追问"布隆过滤器的误判率如何控制"——增加哈希函数个数和位数组大小可以降低误判率，但会增加内存开销。

#### Q7：消息队列如何实现削峰填谷？如何保证消息不丢失？

**回答思路**：削峰填谷的本质是将"同步的瞬时流量"转化为"异步的平稳流量"。秒杀产生的海量请求先进入消息队列，消费者按照自身最大处理能力（如每秒 5000 笔）平稳消费，队列充当缓冲区。

消息可靠性从三个层面保障：生产者端使用确认机制（ACK），确保消息到达 Broker；Broker 端开启持久化和多副本（Kafka 的 ISR、RocketMQ 的同步刷盘）；消费者端关闭自动 ACK，业务成功后手动提交。最后补充：即使三层都做到，业务层仍需保证幂等消费，因为 at-least-once 语义下消息可能被重复投递。

#### Q8：限流有哪些算法？各自的适用场景是什么？

**回答思路**：四种主流算法。

固定窗口计数器——实现简单，但存在临界点突刺问题（窗口切换瞬间可能 2 倍流量）。

滑动窗口——将窗口细分为多个小格，平滑了临界点问题，但实现复杂。

漏桶（Leaky Bucket）——以恒定速率处理请求，能平滑流量但无法应对突发。

令牌桶（Token Bucket）——以恒定速率生成令牌，允许一定程度的突发（桶中积累的令牌可被瞬时消耗），是实践中最常用的算法。Sentinel 和 Nginx 的限流都基于令牌桶。

面试官可能追问"分布式限流怎么做"——单机限流用本地计数器/令牌桶即可；集群限流需要引入 Redis（如 Redis + Lua 实现分布式令牌桶）或专门的限流服务。

#### Q9：熔断、降级、限流的区别和配合方式是什么？

**回答思路**：三者定位不同但协同工作。限流在入口处控制"总流量速率"，防止系统被压垮；熔断在调用链上隔离"下游故障"，防止雪崩效应；降级在系统层面"主动关闭非核心功能"，保障核心链路。

在大促场景中的配合方式：限流控制总入口流量（挡住 30% 的超量请求）→ 熔断隔离非核心服务故障（评论服务挂了不影响下单）→ 降级关闭非核心功能（关闭推荐、实时评价）→ 核心交易链路正常运行。能画出这个流量漏斗图会是加分项。

#### Q10：如何设计一个高并发的秒杀系统？

**回答思路**：秒杀是综合考题，需要从前端到后端全链路设计。

前端层：按钮防重复点击 + 答题/验证码分散峰值（将瞬时流量平摊到 5-10 秒）+ 静态资源 CDN。

网关层：IP/用户维度限流 + 恶意请求拦截 + 黑名单过滤。

应用层：秒杀服务独立部署（与主站隔离）+ 请求排队（消息队列削峰）+ 快速失败（库存为 0 直接返回，不走数据库）。

数据层：Redis Lua 脚本原子扣减库存做第一道拦截 + 数据库乐观锁（`WHERE stock >= #{num}`）兜底 + 异步落库（消息队列）。

兜底层：服务降级（关闭非核心功能）+ 隔离部署（独立集群）。

面试官追问"如何防超卖"——Redis Lua 脚本保证原子判断 + 数据库乐观锁双重保障；"如何保证用户体验"——预扣减成功返回"排队中"，异步处理后推送结果。

#### Q11：如何保证缓存与数据库的一致性？

**回答思路**：这是最容易踩坑的面试题。最常用的策略是 Cache Aside：先更新数据库，再删除缓存（而非更新缓存）。"先更新数据库再删缓存"比"先删缓存再更新数据库"更安全——后者在并发读写时会出现脏数据（线程 A 删缓存 → 线程 B 读数据库旧值写入缓存 → 线程 A 更新数据库 → 缓存中是旧值）。

对于删缓存失败的极端情况，可以使用延迟双删——更新数据库后先删一次缓存，等一小段时间（覆盖一次读请求写回缓存的时间）再删一次。

对于强一致性场景（如支付后查订单），绕过缓存直接查数据库，或使用 Canal 订阅 binlog 异步更新缓存。

面试官追问"为什么用删除缓存而非更新缓存"——并发更新可能出现旧值覆盖新值（A 更新 DB 为 1，B 更新 DB 为 2，但 B 的缓存更新先执行、A 的后执行，导致缓存值为 1 而数据库为 2）。

#### Q12：什么是无状态设计？为什么它是水平扩展的前提？

**回答思路**：无状态设计指应用层不保存任何会话状态——Session 放入 Redis、文件放入对象存储、本地不保存任何用户上下文。这样任何一个实例都可以处理任何请求，负载均衡器可以自由地将请求分发到任意节点。如果应用有状态（如 Session 存在本地内存），那么同一个用户的请求必须始终路由到同一个实例（粘性会话），这会限制负载均衡的灵活性，也无法做到弹性扩缩容（新增实例无法处理已有用户的请求）。

#### Q13：全链路压测是什么？为什么要做数据隔离？

**回答思路**：全链路压测是在生产环境中模拟真实的大促流量，测试系统在高并发下的表现。它比离线压测更准确，因为它使用的是真实的网络环境、真实的数据库、真实的缓存。

数据隔离是必须的——压测产生的数据（订单、支付、库存变更）不能污染真实业务数据。常用方案是影子库/影子表：压测请求被打上标记（如 HTTP Header 中的压测标识），中间件（数据库、缓存、消息队列）识别到标记后将数据路由到影子库/影子表，与真实数据完全隔离。压测结束后影子数据可以被安全清理。

#### Q14：JVM 在高并发场景下如何调优？

**回答思路**：JVM 调优的核心目标是减少 GC 停顿时间、提高吞吐量。

选择合适的 GC 收集器：CMS 适合低延迟场景（停顿时间短但会产生内存碎片）；G1 在延迟和吞吐量之间平衡（适合大多数 Web 应用）；ZGC/Shenandoah 适合超大堆内存和超低延迟要求。

堆内存设置：`-Xms` 和 `-Xmx` 设置为相同值，避免运行时扩缩容带来的停顿。一般设置为物理内存的 50%-70%。

关键参数：设置 `-XX:+PrintGCDetails` 和 `-Xloggc` 输出 GC 日志用于分析；设置 `-XX:MetaspaceSize` 避免元空间动态扩展导致的 Full GC。

面试官可能追问"GC 日志怎么分析"——关注 Full GC 频率（应少于 Young GC 的 1/10）、单次停顿时间（Young GC < 100ms，Full GC < 500ms）、GC 后老年代占用率（如果持续增长可能存在内存泄漏）。

#### Q15：如何设计一个支撑双 11 的高并发电商系统？

**回答思路**：这是最高频的综合设计题，建议按分层架构回答。

流量入口层：CDN 静态加速（承担 70% 流量）+ DNS 智能解析 + API Gateway 限流鉴权。

前端层：资源合并减少请求 + 按钮防重 + 答题分散峰值。

应用层：微服务按业务域拆分 + 秒杀服务独立隔离 + 无状态设计 + K8s 弹性扩缩容。

缓存层：多级缓存（本地 + Redis）+ 热点数据预热 + 防穿透/击穿/雪崩。

消息层：RocketMQ 异步解耦 + 削峰填谷 + 事务消息。

数据层：读写分离 + 分库分表 + ES 异构索引 + Redis Lua 原子扣减 + 数据库乐观锁兜底。

服务治理层：限流（令牌桶）+ 熔断（隔离故障）+ 降级（关闭非核心）+ 全链路压测（影子库隔离）。

可观测性层：日志/指标/链路追踪三件套 + 秒级监控告警 + 预案自动触发。

如果能提到"灰度发布 + 一键回滚"和"流量预热（大促前小流量预热连接池和缓存）"，会是加分项。

### 总结

高并发系统设计的本质是在极端流量压力下保持系统的可控稳定性。它不是单一技术的堆砌，而是从网络 I/O 模型、并发模型、缓存策略、异步解耦、池化技术、限流熔断、数据库优化到弹性扩展的全链路协同。

在电商大促这样的极端场景中，没有任何单一策略能解决问题——CDN 挡住静态流量，多级缓存拦截读请求，消息队列缓冲写请求，限流控制总量，熔断隔离故障，降级保护核心，弹性扩容应对峰值。每一层都有其定位和边界，理解每种技术的适用场景和代价，才能设计出既高性能又稳定的高并发系统。
