# Dify 完整使用指南：从零搭建你的私有 AI 应用开发平台

## 一、Dify 是什么？—— 重新定义 LLM 应用开发

Dify 是一款开源的大语言模型（LLM）应用开发平台，定位为"生产级 Agentic 工作流开发平台"。它的核心理念是 **Backend as a Service + LLMOps**，即把大模型应用开发中涉及的后端基础设施、模型调用、数据管道、运维监控等复杂环节封装为一站式服务，让开发者乃至非技术人员都能通过可视化界面快速构建、部署和管理 AI 应用。

简单来说，如果把大语言模型比作一台强大的引擎，Dify 就是帮你把这台引擎装进汽车里、连上方向盘和油门的整车生产线。你不需要从零写代码对接模型 API、处理上下文管理、搭建向量数据库，只需要在 Dify 提供的画布上拖拽节点、配置参数，就能快速产出一个可以投入实际使用的 AI 应用。

Dify 可以用来做什么？以下是它最典型的几个使用方向：

**企业知识库问答**：将公司的规章制度、技术文档、产品手册等上传至 Dify，系统自动进行文档解析、文本切分和向量化存储，构建一个基于 RAG（检索增强生成）的智能问答系统。员工可以用自然语言提问，系统从知识库中检索相关内容并由大模型生成精准回答。

**智能客服与对话助手**：搭建面向客户的多轮对话系统，支持意图识别、知识库检索、工单创建等复杂流程，并可对外发布为 Web 嵌入组件或 API 接口。

**AI 工作流自动化**：通过可视化画布编排复杂的 AI 工作流，将数据查询、文本生成、API 调用、条件判断等环节串联起来，实现从数据输入到结果输出的全自动化处理。

**内容创作与营销**：自动生成营销文案、产品描述、社交媒体帖子，支持多格式适配和团队协同审阅。

**数据分析助手**：业务人员通过自然语言与数据对话，系统自动读取数据源、执行分析并生成可视化图表，大幅降低数据分析的技术门槛。

Dify 目前已在全球范围内拥有超过 **500 万次下载**、**800 多位社区贡献者**，并驱动着超过 **100 万个运行中的应用**。沃尔沃汽车、理光等知名企业也在生产环境中使用 Dify 来加速 AI 落地。

### 2.2 技术栈总览

Dify 的技术架构由以下几个核心层次组成：

**前端层**：基于 Next.js + TypeScript 构建，采用混合渲染模式（SSR + CSR），提供流畅的单页应用体验。工作流编辑器使用了 React Flow 等可视化组件库，实现了拖拽式的节点编排。

**后端层**：采用 Python + Flask/FastAPI 异步框架，提供 RESTful API 服务。业务逻辑涵盖模型调度、工作流引擎、RAG 管道、用户管理等核心模块。

**数据层**：PostgreSQL 作为关系型数据库存储用户数据、应用配置和运行日志；Redis 用于高速缓存和消息队列；向量数据库（默认 Weaviate，可切换为 pgvector、Milvus、Qdrant 等）负责文档向量的存储与检索。

**基础设施层**：Docker + Docker Compose 实现一键容器化部署，同时支持 Kubernetes（Helm Charts）、Terraform（Azure/GCP）、AWS CDK 等企业级部署方案。

### 2.3 核心组件与服务架构

Dify 的 Docker Compose 部署包含以下关键服务组件：

**API 服务（api）**：核心后端服务，端口 5001，负责处理所有 API 请求，包括模型调用、工作流执行、知识库管理等。

**Web 前端（web）**：用户界面服务，端口 3000，提供工作流编辑器、对话界面、管理控制台等交互功能。

**Worker（worker）**：异步任务处理器，负责执行耗时较长的后台任务，如文档解析、向量索引构建、批量数据处理等，不直接暴露外部端口。

**PostgreSQL（db）**：关系型数据库，存储应用配置、用户数据、对话历史、运行日志等结构化信息。

**Redis（redis）**：内存缓存与消息队列，用于会话状态管理、API 响应缓存和任务调度。

**向量数据库（weaviate/qdrant）**：专门存储文档的向量表示，支持语义相似度检索，是 RAG 管道的基础设施。

**Nginx（nginx）**：反向代理服务器，统一入口，将前端请求和 API 请求路由到对应的后端服务。

**Sandbox（sandbox）**：安全沙箱环境，用于安全执行用户在工作流中编写的代码片段（如 Python/JavaScript），防止恶意代码影响宿主系统。

**Plugin Daemon（plugin_daemon）**：插件守护进程，管理所有已安装的插件生命周期，支持动态扩展平台能力。

**SSRF Proxy（ssrf_proxy）**：安全代理，防止服务端请求伪造（SSRF）攻击，保护系统在调用外部 API 时的网络安全。

## 三、Dify 功能特点

### 3.1 可视化工作流编排

Dify 最核心的能力是其可视化工作流编辑器。用户可以在拖拽式画布上构建复杂的 AI 处理流程，无需编写代码。工作流支持以下节点类型：

**LLM 节点**：调用大语言模型进行文本生成、摘要、翻译等任务，支持配置提示词模板、温度、Top-P 等参数。

**知识检索节点**：从已创建的知识库中检索与用户问题相关的文档片段，支持语义搜索和关键词搜索的混合模式。

**条件分支节点**：根据上游输出结果进行条件判断，将流程路由到不同的处理分支。

**代码执行节点**：在安全沙箱中运行 Python 或 JavaScript 代码，处理数据转换、计算等逻辑。

**HTTP 请求节点**：调用外部 API 接口，实现与第三方服务的数据交互。

**迭代节点**：对列表数据进行批量处理，逐一执行相同的处理逻辑。

**变量聚合节点**：将多个分支的输出汇聚到一起，统一处理后再传递给下游节点。

**Answer 节点**：在对话场景中实时输出中间结果，提升用户体验。

工作流编辑器还支持实时调试，可以在每个节点查看输入输出日志，快速定位和排查问题。

### 3.2 广泛的模型兼容性

Dify 兼容 OpenAI API 标准，能够无缝对接数百种开源和商用大语言模型：

**主流商业模型**：OpenAI GPT 系列、Anthropic Claude 系列、Google Gemini、Cohere 等。

**开源模型**：Meta Llama 3、Mistral、Qwen（通义千问）、DeepSeek、ChatGLM 等。

**本地模型**：通过 Ollama 集成，可在本地运行 Llama、Mistral、Phi 等开源模型，数据完全不出本地网络，适合对隐私要求极高的场景。

**多模态模型**：支持接入图像理解、语音识别等多模态能力。

Dify 的模型管理界面允许开发者轻松切换底层模型、对比不同模型的输出效果，并进行 A/B 测试，帮助选择最适合业务场景的模型方案。

### 3.3 RAG 知识库引擎

Dify 内置了完整的 RAG（检索增强生成）管道，覆盖文档从上传到检索的全生命周期：

**多格式支持**：可解析 PDF、DOCX、PPTX、XLSX、TXT、Markdown、CSV 等 15+ 种文件格式。

**智能分块**：自动对长文档进行文本切分，支持自定义分块大小和重叠比例，还可选择 Q&A 分块模式以提升检索精度。

**向量嵌入**：将文本块转换为向量表示并存储到向量数据库中，支持多种嵌入模型。

**混合检索**：同时支持语义相似度搜索和关键词全文搜索，并可配置 Reranking 重排序模型来优化检索结果的排序。

**引用溯源**：生成的回答会附带引用来源，用户可以点击查看原始文档片段，确保信息可追溯、可验证。

### 3.4 智能体（Agent）能力

Dify 支持构建具备自主推理和工具调用能力的智能体，提供三种 Agent 策略：

**Function Calling（函数调用）**：模型根据用户意图自动选择并调用预定义的工具函数，适合结构化任务，如天气查询、数据库查询、计算器运算等。

**ReAct（推理+行动）**：模型交替进行"思考"和"行动"，先分析问题、制定计划，再调用工具执行，适合需要多步推理的复杂场景。

**ReWOO（无观察推理）**：预先规划完整的工具调用序列后再统一执行，减少模型调用次数，节省算力和延迟。

平台内置 50+ 开箱即用的工具，包括 Google Search、DALL·E 图像生成、Stable Diffusion、WolframAlpha 数学计算等，并支持用户通过 OpenAPI Schema 自定义工具。

### 3.5 Prompt IDE 提示词工作台

Dify 提供了一个专业的提示词开发环境：

**Prompt 编辑器**：支持 Jinja2 模板语法，可以用条件判断、循环等逻辑构建动态提示词，远比简单的字符串拼接灵活。

**模型对比**：同一个提示词可以同时发送给多个模型，并排查看各模型的输出效果。

**上下文管理**：通过变量赋值节点维持对话上下文的连贯性，确保多轮对话的质量。

**语音合成测试**：支持测试文本转语音效果。

### 3.6 LLMOps 运维与监控

Dify 提供了全链路的应用运维能力：

**日志追踪**：记录每一次 API 调用的完整链路，包括输入、输出、延迟、Token 消耗等。

**性能分析**：可视化展示各模型和工作流的响应时间、成功率、错误率等指标。

**标注优化**：在生产环境中对模型回答进行标注（正确/错误/改进），标注数据可导出为微调训练集，形成持续优化的闭环。

**可观测性集成**：支持接入 Langfuse、Opik、Arize Phoenix 等主流 LLM 可观测性平台。

### 3.7 插件系统与 MCP 集成

Dify 拥有活跃的插件生态系统：

**插件市场**：通过插件即时扩展平台能力，接入更多模型和工具，无需修改核心代码。

**MCP 客户端**：Dify 可以作为 MCP 客户端连接外部 MCP 服务端，获取更多工具和数据源。

**MCP 服务端**：Dify 构建的 AI 应用也可以发布为 MCP Server，供其他 MCP 客户端调用，实现跨平台的能力互通。

### 3.8 企业级安全与权限

**RBAC 权限控制**：基于角色的细粒度访问控制，不同角色（管理员、编辑者、普通用户）拥有不同的操作权限。

**SSO 单点登录**：企业版支持接入企业身份认证系统。

**数据隔离**：多租户架构确保不同团队的数据相互隔离。

**审计日志**：记录所有用户操作，满足合规审计需求。

## 四、安装部署与初始化使用

### 4.1 系统要求

在部署 Dify 之前，请确保你的环境满足以下最低要求：

| 项目 | 最低要求 |
|------|----------|
| CPU | 2 核及以上 |
| 内存 | 4 GB 及以上（推荐 8 GB） |
| 磁盘空间 | 20 GB 及以上 |
| Docker | 19.03 及以上 |
| Docker Compose | v2.0.0 及以上（推荐 v2.24.0+） |

### 4.2 标准 Docker Compose 部署

以下是在标准 Linux 服务器或 Mac/Windows（WSL2）环境下的部署步骤。

**第一步：获取源码**

```bash
git clone https://github.com/langgenius/dify.git
cd dify
```

如果网络较慢，可以使用 GitHub 镜像或下载 ZIP 压缩包后解压。

**第二步：准备环境变量**

```bash
cd docker
cp .env.example .env
```

`.env` 文件包含了 Dify 运行所需的所有配置项。对于标准部署，大多数默认值无需修改。如需自定义，重点关注以下参数：

```ini
# 基础配置
CONSOLE_WEB_URL=http://your-domain.com   # 控制台访问地址
SECRET_KEY=your-random-secret-key        # 加密密钥，建议替换为随机字符串

# 端口配置
WEB_PORT=3000        # 前端端口
API_PORT=5001        # API 端口
NGINX_PORT=80        # Nginx HTTP 端口

# 数据库配置
DB_USERNAME=postgres
DB_PASSWORD=difyai123456   # 建议修改为强密码
DB_DATABASE=dify

# Redis 配置
REDIS_PASSWORD=difyai123456  # 建议修改为强密码

# 存储配置
STORAGE_TYPE=local          # local 或 s3
```

**第三步：启动服务**

```bash
docker compose up -d
```

首次启动会拉取所有必要的镜像，耗时取决于网络速度。启动完成后，可以通过以下命令验证所有服务的状态：

```bash
docker compose ps
```

确保所有容器状态均为 `Up` 或 `healthy`。

**第四步：初始化配置**

在浏览器中访问 `http://localhost/install`（如果是远程服务器，替换为实际 IP 地址），进入初始化页面。在此页面中设置管理员账户（邮箱和密码），完成后即可使用设置的凭据登录 Dify 工作台。

### 4.3 NAS 专项部署指南

NAS 设备（如绿联 NAS、群晖 NAS）的 Docker 环境有一些特殊性，需要对标准配置进行适当调整。以下是针对 NAS 的部署要点。

#### 4.3.1 获取并上传源码

对于不熟悉 Git 的用户，可以直接在 GitHub Releases 页面下载最新版本的 ZIP 压缩包，通过 NAS 的文件管理器上传到指定目录并解压。建议将 Dify 的 `docker` 目录放在 NAS 的 Docker 专用存储路径下，例如：

- 绿联 NAS：`/volume1/docker/dify/`
- 群晖 NAS：`/volume1/docker/dify/`

#### 4.3.2 修改 Docker Compose 配置

NAS 环境需要对 `docker-compose.yaml` 进行以下调整：

**移除不必要的服务**：

NAS 通常不需要自带的证书申请和 Nginx 服务（可以使用 NAS 自带的反向代理），建议注释或移除以下服务定义：

```yaml
# 注释掉 certbot 服务（NAS 不需要自动申请证书）
# certbot:
#   ...

# 注释掉 nginx 服务（使用 NAS 自带的反向代理）
# nginx:
#   ...
```

**移除 OpenSearch 服务**（如果存在）：

部分版本的 Dify 默认配置中包含 OpenSearch，其极限参数设置在 NAS 上可能导致容器管理器报错。系统默认的向量数据库是 Weaviate，移除 OpenSearch 不影响正常使用。

**修改端口映射**：

NAS 上可能已有其他服务占用了 80/443 端口，需要将 Dify 的端口映射到空闲端口：

```yaml
services:
  api:
    ports:
      - '5301:5001'    # API 端口映射到 5301
  
  web:
    ports:
      - '5300:3000'    # Web 前端端口映射到 5300
```

如果保留了 Nginx 服务，则修改 Nginx 的端口映射：

```yaml
services:
  nginx:
    ports:
      - '11180:80'     # HTTP
      - '11443:443'    # HTTPS
```

**移除资源限制**（绿联 NAS）：

绿联 NAS 社区反馈，compose 文件中某些资源限制配置可能导致部署失败，建议删除或注释掉相关的 `deploy.resources` 段落。

#### 4.3.3 创建持久化目录

在 compose 文件所在目录下，手动创建以下持久化存储目录，防止容器重启后数据丢失：

```bash
mkdir -p volumes/app/storage
mkdir -p volumes/db/data
mkdir -p volumes/redis/data
mkdir -p volumes/weaviate/data
mkdir -p volumes/plugin/data
```

#### 4.3.4 启动与验证

通过 NAS 的 Docker 管理界面（如绿联的"容器管理器"或群晖的"Container Manager"）创建新项目，选择修改后的 `docker-compose.yaml` 文件进行部署。或者通过 SSH 登录后执行：

```bash
cd /volume1/docker/dify
docker compose up -d
```

启动完成后，通过 `docker compose ps` 确认所有容器运行正常。

#### 4.3.5 配置反向代理（可选）

如果希望通过域名访问 Dify 而非直接使用 IP:端口，可以在 NAS 上配置反向代理。以 Nginx Proxy Manager 为例：

**前端代理**：将域名指向 NAS 内网 IP + Web 端口（如 `192.168.1.100:5300`）。

**API 代理**：添加以下 Custom Locations，统一转发到 API 端口（如 `192.168.1.100:5301`）：

```
/console/api  →  192.168.1.100:5301
/api          →  192.168.1.100:5301
/v1           →  192.168.1.100:5301
/files        →  192.168.1.100:5301
```

#### 4.3.6 NAS 部署常见问题

**PostgreSQL 连接超时（dial error）**：通常由 NAS 防火墙导致。解决方法是在 NAS 防火墙设置中放行 Docker 子网段（一般为 `172.17.0.0/16` 和 `172.18.0.0/16`）。

**容器启动失败报路径不存在**：确保已提前手动创建所有持久化目录。

**端口冲突**：NAS 自带的 Web 管理界面可能占用了 80/443/5000 等端口，务必为 Dify 选择不冲突的端口。

**YAML 语法错误**：修改 compose 文件时注意保持正确的缩进格式，YAML 使用空格缩进，严禁使用 Tab。

### 4.4 初始化使用入门

完成部署和初始化后，按照以下步骤开始使用 Dify：

**Step 1：配置模型供应商**

登录工作台后，首先进入"设置 → 模型供应商"页面。Dify 支持同时接入多个模型供应商。最常用的配置方式：

- **OpenAI**：填入 API Key 即可。
- **本地 Ollama**：填入 Ollama 服务的地址（如 `http://host.docker.internal:11434`），无需 API Key。
- **其他兼容 OpenAI API 的服务**：填入 Base URL 和 API Key。

**Step 2：创建第一个应用**

点击"创建应用"，Dify 提供四种应用类型：

- **Chatbot（对话型应用）**：最简单的方式，适合快速搭建聊天助手。
- **Text Generator（文本生成器）**：适合单次文本生成任务，如翻译、摘要。
- **Agent（智能体）**：具备工具调用能力，可以搜索网页、查天气等。
- **Workflow（工作流）**：最灵活的方式，适合复杂的自动化处理流程。

新手建议先从"对话型应用"开始，选择一个预置模板（如"知识库问答"）快速体验。

**Step 3：创建知识库并上传文档**

在"知识库"页面点击"创建知识库"，上传你的文档文件。Dify 会自动进行文档解析和索引构建。你可以调整以下参数来优化检索效果：

- **分段大小**：控制每个文本块的长度，建议 300-500 字符。
- **重叠大小**：相邻文本块的重叠部分，建议 50-100 字符。
- **索引方式**：高质量模式（使用嵌入模型）或经济模式（仅关键词搜索）。

**Step 4：编排工作流**

对于 Workflow 类型的应用，进入工作流编辑器，从节点面板拖入所需节点，连接它们形成完整的处理流程。每个节点都可以独立测试和调试。

**Step 5：发布与分享**

应用调试通过后，点击"发布"按钮。Dify 提供多种发布方式：

- **Web 链接**：生成一个独立的访问链接，任何人打开即可使用。
- **嵌入组件**：生成一段嵌入代码，可以放置在任何网页中。
- **API 接口**：通过 API 端点将能力集成到自己的业务系统中。

### 4.5 版本升级

Dify 更新频繁，升级时请注意：

1. 备份当前的 `.env` 文件和数据库数据。
2. 拉取最新代码：`git pull`。
3. 对比最新的 `.env.example` 与你的 `.env` 文件，补充新增的配置项。
4. 重新构建并启动：`docker compose down && docker compose up -d`。

不同版本的升级步骤可能有细微差异，建议升级前查看 GitHub Releases 页面中对应版本的升级说明。

## 五、进阶使用与实战案例

### 5.1 实战案例一：企业知识库问答系统

**场景描述**：公司内部有大量技术文档、产品手册和规章制度，分散在不同系统中。员工经常需要花大量时间查找信息。目标是构建一个统一的智能问答系统，员工用自然语言提问即可获得准确答案。

**搭建步骤**：

1. **创建知识库**：在 Dify 中创建多个知识库，分别对应不同类型的文档（技术文档、产品手册、HR 政策等）。
2. **上传与处理**：批量上传 PDF、DOCX、PPTX 等格式的文档，调整分块参数。对于技术文档，建议采用 Q&A 分块模式，将常见问题和答案预提取为独立段落。
3. **构建 Chatflow**：创建一个对话型工作流，流程如下：
   - 起始节点接收用户提问。
   - 意图分类节点判断问题属于哪个知识领域。
   - 条件分支路由到对应的知识库检索节点。
   - LLM 节点结合检索结果生成回答。
   - 条件分支评估回答的置信度，高置信度直接返回，低置信度提示用户联系相关部门。
4. **发布与集成**：将应用嵌入公司内部网站或对接企业 IM 机器人。

**效果**：某企业实际部署后，系统服务超过 19,000 名员工、横跨 20+ 个部门，文档查找时间从平均 15 分钟缩短到秒级响应。

### 5.2 实战案例二：智能客服工作流

**场景描述**：电商客服团队每天处理大量重复性咨询，包括订单查询、退换货政策、物流追踪等。目标是用 AI 自动处理 80% 的常见问题，将人工客服从重复劳动中解放出来。

**搭建步骤**：

1. **知识库准备**：将退换货政策、常见问题 FAQ、物流规则等文档导入知识库。
2. **工作流编排**：
   - 起始节点接收客户消息。
   - 意图识别节点将消息分类为：订单查询、退换货咨询、物流追踪、其他。
   - 订单查询分支：通过 HTTP 请求节点调用订单系统 API，查询订单状态后由 LLM 生成友好的回复。
   - 退换货咨询分支：从知识库检索相关政策，LLM 生成答复并附上政策引用。
   - 物流追踪分支：调用物流查询 API，格式化输出物流信息。
   - 兜底逻辑：当 AI 无法处理时，自动创建工单并转交人工客服。
3. **工具集成**：配置订单系统 API、物流查询 API 作为自定义工具。
4. **持续优化**：根据标注数据不断优化意图识别的准确率和回答质量。

### 5.3 实战案例三：AI 内容创作工作台

**场景描述**：营销团队需要为不同平台（官网、微信公众号、小红书、抖音）生成格式各异的营销文案，同时确保品牌调性一致、内容合规。

**搭建步骤**：

1. **品牌知识库**：上传品牌手册、过往优秀文案、合规审查标准等文档。
2. **多步骤工作流**：
   - 输入节点接收产品信息和目标受众描述。
   - LLM 节点生成初稿，提示词中注入品牌调性要求。
   - 迭代节点为每个目标平台生成适配版本（官网长文、公众号图文、小红书笔记、短视频脚本）。
   - 代码执行节点进行合规检查（敏感词过滤、法规条款校验）。
   - 最终输出节点将所有版本汇总展示。
3. **Prompt 优化**：使用 Jinja2 模板根据产品类型动态切换提示词模板。

### 5.4 实战案例四：数据分析助手

**场景描述**：业务分析师需要频繁从数据库中提取数据并制作报表，但 SQL 编写能力有限。目标是让业务人员用自然语言描述需求，系统自动查询数据并生成可视化图表。

**搭建步骤**：

1. **数据库连接**：通过自定义工具或 HTTP 请求节点连接内部数据 API。
2. **工作流设计**：
   - 起始节点接收自然语言问题（如"上个季度各区域销售额对比"）。
   - LLM 节点将自然语言转换为 SQL 查询语句。
   - 代码执行节点运行 SQL 并返回结果数据。
   - LLM 节点分析数据结果，生成文字解读。
   - 代码执行节点使用 Python 可视化库（如 Matplotlib）生成图表。
3. **安全控制**：SQL 执行节点限定只读权限，并设置查询超时和数据量限制。

### 5.5 实战案例五：接入 Ollama 实现完全本地化部署

**场景描述**：对数据隐私有严格要求的团队，希望所有数据处理都在本地完成，不依赖任何外部云服务。

**搭建步骤**：

1. **安装 Ollama**：在 NAS 或本地服务器上安装 Ollama（[ollama.com](https://ollama.com/)）。
2. **拉取模型**：

```bash
ollama pull llama3          # Meta Llama 3
ollama pull qwen2.5         # 通义千问 2.5
ollama pull nomic-embed-text  # 嵌入模型
```

3. **配置 Dify 连接 Ollama**：
   - 在 Dify 的"模型供应商"页面添加 Ollama。
   - 填入 Ollama 服务地址。如果 Ollama 和 Dify 运行在同一台机器的 Docker 中，使用 `http://host.docker.internal:11434`（Mac/Windows）或 Docker 网络内部地址（Linux）。
   - 选择已拉取的模型进行添加。
4. **使用**：创建应用时选择 Ollama 提供的模型，所有推理完全在本地完成，数据不出内网。

### 5.6 API 集成开发示例

Dify 创建的应用都可以通过 API 对外提供服务。以下是一个 Python SDK 调用示例：

```python
from dify_client import ChatClient

# 初始化客户端
api_key = "app-xxxxxxxxxxxxxxxx"  # 在应用设置页面获取 API Key
client = ChatClient(api_key)

# 发送对话请求
response = client.create_chat_message(
    inputs={},
    query="请帮我总结一下这份报告的关键要点",
    user="user-123",
    response_mode="blocking"
)

print(response.get("answer"))
```

工作流应用的调用方式类似：

```python
from dify_client import CompletionClient

api_key = "app-yyyyyyyyyyyyyyyy"
client = CompletionClient(api_key)

response = client.create_completion_message(
    inputs={
        "product_name": "智能手表 X1",
        "target_audience": "年轻科技爱好者",
        "platform": "小红书"
    },
    user="user-456",
    response_mode="blocking"
)

print(response.get("task_id"))
```

### 5.7 性能优化建议

**知识库优化**：根据文档类型定制分块规则，技术文档适合较小的分块（200-300 字符）以保持精确性，叙事性文档可以使用较大的分块（500-800 字符）以保持上下文连贯。启用 Reranking 重排序模型可以显著提升多文档联合检索的准确度。

**工作流优化**：使用变量聚合节点收敛复杂分支的输出，避免下游节点接收到过多冗余信息。使用迭代节点处理批量任务时，注意设置合理的并发限制，防止 API 过载。

**模型选择策略**：对于意图分类、格式转换等简单任务使用小模型（如 GPT-3.5-turbo 或 Qwen-7B）以降低成本和延迟；对于复杂推理和创意生成使用大模型（如 GPT-4 或 Claude 3）。

**缓存策略**：对于高频问题，可以在工作流中加入缓存逻辑，将 LLM 的回答缓存到 Redis 中，相同问题直接返回缓存结果。
